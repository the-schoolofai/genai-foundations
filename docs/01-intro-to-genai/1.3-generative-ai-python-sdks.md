### 1.3 Generative AI Python SDKs

---

## 1. What Is a Python SDK for Generative AI?

An **SDK (Software Development Kit)** is a ready-made Python library from an AI company that lets your code talk to its models in a few lines, without writing raw HTTP requests.

### Module, Library, SDK, API

| Term | What it is | Example |
|---|---|---|
| **Module** | A single `.py` file with reusable code | `os`, `json`, your own `llm.py` |
| **Library (package)** | A collection of modules you install | `pydantic`, `requests` |
| **SDK** | A library built for one platform's API, with types, errors, streaming, and retries | `openai`, `anthropic`, `google-genai`, `ollama` |
| **API** | The service on the provider's servers that the SDK talks to | Chat Completions, Responses, Messages |

> **Mental Model: The Restaurant**
> The **API** is the kitchen. The **SDK** is the waiter who speaks the kitchen's language. Your code just tells the waiter what you want.

---

## 2. The API Styles You Must Know

Every provider exposes its models through an API "shape." Four shapes dominate the industry in 2026.

| API | Provider | Call in Python | Status in 2026 |
|---|---|---|---|
| **Chat Completions** | OpenAI (2023) | `client.chat.completions.create(...)` | The universal standard; copied by almost every provider |
| **Responses API** | OpenAI (2025) | `client.responses.create(...)` | OpenAI's primary API for new projects |
| **Messages API** | Anthropic | `client.messages.create(...)` | Claude's native API |
| **Interactions API** | Google | `client.interactions.create(...)` | Gemini's recommended API (GA June 2026); `generateContent` is still supported |

Ollama also has its own native API (`chat`, `generate`), which you used in Lesson 1.2.

> **Mental Model: Chat Completions Is the USB Port of GenAI**
> Because OpenAI's Chat Completions format became the de facto standard, most providers offer an **OpenAI-compatible endpoint**. Learn one SDK (`openai`), and you can plug into Ollama, Gemini, DeepSeek, Qwen, GLM, Grok, and more by changing only the `base_url`, the `api_key`, and the `model`.

## 3. Native Python SDKs by Provider

| Provider | Model family | Native SDK (`uv add ...`) | OpenAI-compatible `base_url` |
|---|---|---|---|
| OpenAI | GPT | `openai` | Default (no change) |
| Anthropic | Claude | `anthropic` | `https://api.anthropic.com/v1/` |
| Google | Gemini | `google-genai` | `https://generativelanguage.googleapis.com/v1beta/openai/` |
| Ollama | Local + cloud open models | `ollama` | `http://localhost:11434/v1/` |
| xAI | Grok | `xai-sdk` | `https://api.x.ai/v1` |
| DeepSeek | DeepSeek | No native SDK; use `openai` | `https://api.deepseek.com` |
| Alibaba | Qwen | `dashscope` | `https://dashscope-intl.aliyuncs.com/compatible-mode/v1` |
| Z.ai | GLM | `zai-sdk` | `https://api.z.ai/api/paas/v4/` |
| Mistral AI | Mistral | `mistralai` | `https://api.mistral.ai/v1` |

Endpoints occasionally change. Always confirm the current `base_url` in the provider's documentation.

### Unified Gateways: One Interface, Many Providers

| Tool | Type | What it does |
|---|---|---|
| **LiteLLM** | Open-source Python library and proxy | Calls 100+ providers in OpenAI format; adds cost tracking, fallbacks, and load balancing |
| **OpenRouter** | Hosted service | One API key and one `base_url` (`https://openrouter.ai/api/v1`) for hundreds of models |

> **Mental Model: Native SDK vs Gateway**
> A **native SDK** is a direct flight: fastest access to every new feature of one provider.
> A **gateway** is an airport hub: one ticket gets you anywhere, at the cost of some provider-specific features.

## 5. Setup: Project, Packages, and Secrets

From Lesson 1.2, you have uv and a project folder. Add the two packages you need:

```bash
uv add openai python-dotenv
```

`pydantic` is installed automatically because `openai` depends on it.

### Why Use a `.env` File?

API keys are passwords that cost money. **Never write them in your code.**

| Without `.env` | With `.env` |
|---|---|
| Key is hard-coded in `main.py` | Key lives in a separate file |
| Pushed to GitHub by accident; bots steal it within minutes | Code is safe to share |
| Changing the key means editing code | Change the key without touching code |

Create a file named `.env` in your project folder:

```text
OPENAI_API_KEY=sk-your-openai-key
GEMINI_API_KEY=your-gemini-key
PROVIDER=ollama
```

### Why Use `.gitignore`?

`.gitignore` tells Git which files must **never** be committed. Open `.gitignore` (uv creates one for you) and add:

```text
.env
```

> **Mental Model: The House Key**
> `.env` is where you keep your house key. `.gitignore` is the rule that says "never post the key on social media." You need both.

## 6. From Model Approach to System Approach

| Model approach (beginner) | System approach (industry) |
|---|---|
| Model name and key hard-coded in each script | Configuration lives in one place |
| Switching provider means rewriting code | Switching provider means changing one setting |
| Each script talks to one model | Every script asks a shared module for a client |

> **Mental Model: Power Socket, Not Hard-Wired**
> A hard-wired lamp only works in one spot. A plug fits any socket. Your app should **plug into** a model, not be wired to it.

### Build the System: `llm.py`

Create `llm.py`. This is your own **module**: one place that knows every provider.

```python
import os

from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()

PROVIDERS = {
    "ollama": {
        "base_url": "http://localhost:11434/v1/",
        "api_key_env": None,
        "model": "gemma4:e2b",
    },
    "openai": {
        "base_url": None,
        "api_key_env": "OPENAI_API_KEY",
        "model": "gpt-5.5",
    },
    "gemini": {
        "base_url": "https://generativelanguage.googleapis.com/v1beta/openai/",
        "api_key_env": "GEMINI_API_KEY",
        "model": "gemini-3.8-flash",
    },
}


def get_client(provider: str | None = None) -> tuple[OpenAI, str]:
    provider = provider or os.getenv("PROVIDER", "ollama")
    config = PROVIDERS[provider]

    if config["api_key_env"]:
        api_key = os.getenv(config["api_key_env"])
        if not api_key:
            raise ValueError(f"Add {config['api_key_env']} to your .env file")
    else:
        api_key = "ollama"  # Ollama ignores the key, but the SDK requires one

    client = OpenAI(api_key=api_key, base_url=config["base_url"])
    return client, config["model"]
```

| Line | What it does |
|---|---|
| `load_dotenv()` | Reads `.env` and loads its values into environment variables |
| `PROVIDERS` | One dictionary that describes every provider |
| `os.getenv(...)` | Reads a value from the environment, never from code |
| `raise ValueError(...)` | Stops early with a clear message if a key is missing |
| `OpenAI(api_key=..., base_url=...)` | The same SDK talks to a different provider |
| `return client, config["model"]` | Every script gets a ready client and model name |

To switch providers, change `PROVIDER=ollama` to `PROVIDER=openai` or `PROVIDER=gemini` in `.env`. No code changes.

## 7. Script 1: Your First Call (Chat Completions)

Create `chat.py`:

```python
from llm import get_client

client, model = get_client()

response = client.chat.completions.create(
    model=model,
    messages=[
        {"role": "system", "content": "You are a concise career advisor."},
        {"role": "user", "content": "Give me 3 skills to become a GenAI developer."},
    ],
)

print(response.choices[0].message.content)
```

```bash
uv run chat.py
```

| Part | Meaning |
|---|---|
| `response.choices` | A list of possible answers (usually one) |
| `choices[0].message.content` | The text of the first answer |
| `response.usage` | Tokens used; this is what you pay for |

## 8. Script 2: Streaming with the OpenAI SDK

Create `stream.py`:

```python
from llm import get_client

client, model = get_client()

stream = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "Explain Generative AI in 4 short lines."}],
    stream=True,
)

for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        print(chunk.choices[0].delta.content, end="", flush=True)
print()
```

| Non-streaming | Streaming |
|---|---|
| `response.choices[0].message.content` | `chunk.choices[0].delta.content` |
| One complete message | Many small **deltas** (changes) |

> **Mental Model: Delta = The New Piece**
> Each chunk carries only the **new** text since the last chunk. Your loop glues the deltas together on screen.

The same script works with Ollama, OpenAI, and Gemini. Only `PROVIDER` in `.env` changes.

## 9. Script 3: Structured Output with Pydantic

Real applications need **data**, not paragraphs. Here the model acts as the "judge" from Lesson 1.1: it classifies a support ticket and returns clean, typed data.

Create `structured.py`:

```python
from typing import Literal

from pydantic import BaseModel

from llm import get_client


class Ticket(BaseModel):
    category: Literal["billing", "delivery", "technical", "other"]
    priority: Literal["low", "medium", "high"]
    summary: str


client, model = get_client()

completion = client.chat.completions.parse(
    model=model,
    messages=[
        {"role": "system", "content": "Classify the customer support ticket."},
        {"role": "user", "content": "I was charged twice for my order and need a refund today."},
    ],
    response_format=Ticket,
)

ticket = completion.choices[0].message.parsed
print(ticket)
print("Category:", ticket.category)
print("Priority:", ticket.priority)
```

Example output:

```text
category='billing' priority='high' summary='Customer was charged twice and wants a refund.'
Category: billing
Priority: high
```

| Part | Meaning |
|---|---|
| `class Ticket(BaseModel)` | Defines the exact shape of the answer |
| `Literal[...]` | Only these values are allowed |
| `.parse(..., response_format=Ticket)` | Sends the schema to the model and validates the reply |
| `.message.parsed` | A real Python object, not text |

> **Mental Model: The Form, Not the Essay**
> Without structure, the model writes an essay you must read. With Pydantic, it fills in a **form** your code can use directly: save to a database, route to a team, or trigger an alert.

Small local models follow schemas less reliably than large cloud models. If the local result fails validation, try a larger model or a cloud model.

## 10. Bonus: The Responses API (OpenAI's Newer Design)

The same task using the Responses API with OpenAI:

```python
from llm import get_client

client, model = get_client("openai")

response = client.responses.create(
    model=model,
    instructions="You are a concise career advisor.",
    input="Give me 3 skills to become a GenAI developer.",
)

print(response.output_text)
```

| Chat Completions | Responses API |
|---|---|
| `messages=[...]` with a system message | `instructions=` and `input=` |
| `response.choices[0].message.content` | `response.output_text` |
| Supported by almost every provider | OpenAI-native; Ollama supports it for non-stateful requests |

## Key Takeaways

1. An **SDK** is a library that lets Python talk to a provider's **API** in a few lines.
2. The main API styles are **Chat Completions, Responses, Messages, and Interactions**.
3. **Chat Completions is the universal format**, so the `openai` SDK works with Ollama, Gemini, DeepSeek, Qwen, GLM, Grok, and more.
4. Keep keys in **`.env`** and list `.env` in **`.gitignore`**.
5. Think in **systems, not models**: one `llm.py` module, provider chosen by configuration.
6. **Streaming** improves user experience; **Pydantic structured output** turns AI answers into usable data.

**Practice:** Add a fourth provider (DeepSeek or OpenRouter) to `PROVIDERS` in `llm.py`, and run all three scripts against it without changing any other file.
