### 2.2 Context Windows and Memory

---

## 1. What Is a Context Window?

**The context window is the maximum number of tokens a model can work with in a single request.** It includes everything: the system prompt, the conversation so far, any documents you paste, and the answer the model writes.

```text
+------------------------------- Context window (e.g. 128,000 tokens) -------------------------------+
| System prompt | Earlier messages | Documents | Latest user message |  Model's answer (output)       |
+------------------------------------------------------------------------------------------------------+
               Input tokens                                              Output tokens
```

If input plus output is larger than the window, the request fails, or the oldest text is silently cut.

> **Mental Model: The Desk**
> The context window is the size of the model's desk. Everything it needs must fit on the desk at the same time. A bigger desk holds more papers, but a messy desk makes it harder to find the important page.

---

## 2. LLMs Have No Memory

This is the most important idea in this lesson:

**An LLM is stateless. It remembers nothing between requests.**

When a chatbot "remembers" your name, it is because **the application sends the whole conversation again** with every new message.

| Turn | What the app actually sends to the model |
|---|---|
| 1 | System + "Hi, I'm Ali." |
| 2 | System + "Hi, I'm Ali." + AI reply + "I live in Lahore." |
| 3 | System + "Hi, I'm Ali." + AI reply + "I live in Lahore." + AI reply + "What's my name?" |

Each turn is bigger than the last. Eventually the conversation fills the context window, and the app must decide what to drop.

> **Mental Model: The Goldfish With a Notebook**
> The model is a goldfish: it forgets everything after each answer. The **message list** is a notebook your code hands to the goldfish before every question. "Memory" in GenAI means **managing that notebook**.

---

## 3. Context Window Timeline

| Date | Model | Context window |
|---|---|---|
| Jun 2020 | GPT-3 (OpenAI) | 2,048 tokens |
| Mar 2023 | GPT-4 (OpenAI) | 8,192 and 32,768 tokens |
| May 2023 | Claude (Anthropic) | 100,000 tokens |
| Nov 2023 | GPT-4 Turbo (OpenAI) | 128,000 tokens |
| Nov 2023 | Claude 2.1 (Anthropic) | 200,000 tokens |
| **Feb 2024** | **Gemini 1.5 Pro (Google)** | **1,000,000 tokens** (2M from May 2024) |
| Apr 2025 | GPT-4.1 (OpenAI) | About 1,000,000 tokens |
| Apr 2025 | Llama 4 Scout (Meta) | 10,000,000 tokens |
| 2026 | Claude Opus 5.5 and Sonnet 5.5, latest GPT and Gemini models | About 1,000,000 tokens is now standard at the frontier |

In six years, context windows grew about **500 times**.

### Context Windows You Will Actually Use

| Model | Context window |
|---|---|
| Claude Opus 5.5, Claude Sonnet 5.5 | 1,000,000 tokens |
| Claude Haiku 4.5 | 200,000 tokens |
| Gemma 4 E2B / E4B (local) | 128,000 tokens |
| Gemma 4 12B / 26B / 31B (local) | 256,000 tokens |

**Important for local models:** a model's *maximum* context is not what Ollama uses by default. Ollama sets the default context length based on your GPU memory: **4K tokens below 24 GB of VRAM**, 32K for 24 to 48 GB, and 256K at 48 GB or more. On most student laptops, that means only about **4,000 tokens**. You can raise it with the `num_ctx` option (shown in Section 7), and check it with `ollama ps`.

## 4. Bigger Is Not Always Better

| Problem | What happens |
|---|---|
| **Lost in the middle** (2023 research) | Models use information at the start and end of a long context better than information in the middle |
| **Context rot** (2025 research) | Answer quality drops as the context gets longer, well before the window is full |
| **Cost** | You pay for every input token, every turn; long histories get expensive fast |
| **Speed** | More input tokens means a slower first response |

> **Mental Model: The Briefcase, Not the Warehouse**
> A good engineer does not send the model everything. They send the **right** things, like packing a briefcase for a meeting instead of bringing the whole warehouse. This skill is called **context engineering**.

---

## 5. Memory Strategies for GenAI Applications

| Strategy | How it works | Good for | Weakness |
|---|---|---|---|
| **Full history (buffer)** | Send every message, every turn | Short chats | Grows until it overflows |
| **Sliding window** | Keep only the last N turns | Simple chatbots | Forgets early facts (like the user's name) |
| **Token trimming** | Keep the newest messages that fit a token budget | Production chat apps | Same as sliding window, but safer |
| **Summarization** | Replace old messages with a short summary | Long conversations | Costs an extra model call; details can be lost |
| **Server-side state** | The provider stores the conversation and you send an ID | Quick prototypes | Data is stored by the provider; less control |
| **Persistence (checkpointer)** | Save each conversation to memory or a database by thread ID | Multi-user apps | Needs a framework or database |

### Short-Term vs Long-Term Memory

| | Short-term memory | Long-term memory |
|---|---|---|
| Scope | One conversation (thread) | Across many conversations |
| Example | "Earlier in this chat you said you're Ali" | "Last month you said you prefer Urdu" |
| Built with | Message list, trimming, checkpointer | Databases, vector stores, memory tools |
| Covered in | **This lesson** | Later modules (agents) |

This lesson covers **short-term memory for GenAI applications**. Long-term memory is mostly used by agents and is covered later in the course.

## 6. Memory Timeline: GenAI, LangChain, and Agents

| Date | Milestone | Why it matters |
|---|---|---|
| Jun 2020 | GPT-3 API | Stateless text-in, text-out; developers paste history into the prompt themselves |
| Oct 2022 | LangChain launches | Early `ConversationBufferMemory`, window, and summary memory classes |
| Nov 2022 | ChatGPT | The public sees "memory," built by resending the conversation |
| Mar 2023 | Chat Completions API | The **messages list** becomes the standard way to carry history |
| Jul 2023 | "Lost in the Middle" paper | Shows long context is not used evenly |
| Oct 2023 | MemGPT paper (later Letta) | Treats the context window like computer RAM with memory paging |
| Nov 2023 | OpenAI Assistants API with Threads | First major **server-side** conversation memory |
| 2024 | LangChain `RunnableWithMessageHistory` | Recommended way to attach chat history to LangChain chains |
| Feb 2024 | LangGraph released; ChatGPT Memory announced | **Checkpointers** for short-term memory; ChatGPT remembers facts across chats |
| 2024 | Mem0 | Open-source long-term memory layer for AI apps |
| 2024 | LangChain v0.3.1 | Legacy memory classes (`ConversationBufferMemory` and others) **deprecated** |
| Oct 2024 | LangGraph long-term memory Store | Memory shared **across** conversations |
| Feb 2025 | LangMem SDK | Tools for extracting and managing long-term memories |
| Mar 2025 | OpenAI Responses API | `previous_response_id` chains turns on the server |
| Apr 2025 | ChatGPT references all past chats | Consumer long-term memory goes mainstream |
| Jul 2025 | "Context Rot" report | Quality drops as input length grows |
| Aug 2025 | OpenAI Conversations API | Durable server-side conversation objects; Assistants API scheduled for shutdown |
| Sep 2025 | Anthropic context editing and memory tool | Clears stale context automatically; file-based memory for agents |
| **Oct 2025** | **LangChain 1.0** | Memory moves to **LangGraph persistence**; old memory classes move to `langchain-classic` |
| 2026 | `langchain-core` deprecates `RunnableWithMessageHistory` (1.3.3) and `InMemoryChatMessageHistory` (1.6.4) | LangGraph persistence is the official path for chat history |
| Mar 2026 | LangChain Deep Agents | Filesystem-based long-term memory for agents |
| Jun 2026 | Gemini Interactions API GA | `previous_interaction_id` for server-side history |
| Aug 2026 | OpenAI Assistants API shut down | Replaced by the Responses and Conversations APIs |

> **Mental Model: Three Eras of Memory**
> **2020–2022:** "Paste it yourself" (manual prompt history).
> **2023–2024:** "Framework classes" (LangChain memory classes, server-side threads).
> **2025–2026:** "Persistence and context engineering" (checkpointers, trimming, summarization, memory tools).

### Legacy LangChain Memory: What Not to Use in New Code

You will still see these in older tutorials. Verified against current package versions:

| Old API | Status | Use instead |
|---|---|---|
| `ConversationBufferMemory`, `ConversationSummaryMemory`, `ConversationChain` | Deprecated since 0.3.1; now only in `langchain-classic` | Message list, or LangGraph checkpointer |
| `RunnableWithMessageHistory` | Deprecated in `langchain-core` 1.3.3 | LangGraph persistence |
| `InMemoryChatMessageHistory` | Deprecated in `langchain-core` 1.6.4 | LangGraph persistence |

## 8. Example 1: Ollama Python SDK (Full History)

Create `memory_ollama.py`:

```python
from ollama import chat

MODEL = "gemma4:e2b"

messages = [
    {"role": "system", "content": "You are a friendly support assistant. Keep answers short."},
]

questions = [
    "Hi, my name is Ali and I ordered a laptop.",
    "Can I get it delivered to Lahore?",
    "What is my name and what did I order?",
]

for question in questions:
    messages.append({"role": "user", "content": question})

    response = chat(model=MODEL, messages=messages, options={"num_ctx": 8192})
    reply = response.message.content

    messages.append({"role": "assistant", "content": reply})

    print(f"You: {question}")
    print(f"AI:  {reply}")
    print(f"     [input tokens this turn: {response.prompt_eval_count}]\n")
```

```bash
uv run memory_ollama.py
```

**What to notice:** the input token count **grows every turn**, because the whole history is sent each time.

| Code | Meaning |
|---|---|
| `messages.append({"role": "user", ...})` | Add the new question to the notebook |
| `messages.append({"role": "assistant", ...})` | Save the answer, so the next turn includes it |
| `options={"num_ctx": 8192}` | Raise Ollama's context length for this request |
| `response.prompt_eval_count` | How many input tokens the model read |

**Experiment:** delete the line that appends the assistant reply, and run again. The model loses track of the conversation.

## 9. Example 2: OpenAI Python SDK (Sliding Window)

This uses `llm.py` from Lesson 1.3, so it works with Ollama, OpenAI, or Gemini. It keeps only the **last 2 turns**.

Create `memory_window.py`:

```python
from llm import get_client

client, model = get_client()

SYSTEM = {"role": "system", "content": "You are a friendly support assistant. Keep answers short."}
MAX_TURNS = 2  # one turn = one user message + one assistant reply

history = []


def ask(question: str) -> str:
    history.append({"role": "user", "content": question})

    recent = history[-(MAX_TURNS * 2 + 1):]
    response = client.chat.completions.create(model=model, messages=[SYSTEM] + recent)
    reply = response.choices[0].message.content

    history.append({"role": "assistant", "content": reply})
    return reply


questions = [
    "Hi, my name is Ali and I ordered a laptop.",
    "Can I get it delivered to Lahore?",
    "How long does delivery take?",
    "Do you offer a warranty?",
    "What is my name and what did I order?",
]

for question in questions:
    print(f"You: {question}")
    print(f"AI:  {ask(question)}\n")
```

**What to notice:** by the last question, the turn where Ali introduced himself has slid out of the window. The model **forgets his name**. This is the main weakness of a sliding window.

| Code | Meaning |
|---|---|
| `history[-(MAX_TURNS * 2 + 1):]` | Keep the newest question plus the last 2 full turns |
| `[SYSTEM] + recent` | The system prompt is always kept, never trimmed |

## 10. Example 3: Anthropic Python SDK (Messages API)

Claude's Messages API carries history the same way, with two differences: the **system prompt is a separate parameter**, and **`max_tokens` is required**.

Create `memory_anthropic.py`:

```python
from anthropic import Anthropic
from dotenv import load_dotenv

load_dotenv()

client = Anthropic()  # reads ANTHROPIC_API_KEY from the environment
MODEL = "claude-sonnet-5-5"
SYSTEM = "You are a friendly support assistant. Keep answers short."

messages = []

questions = [
    "Hi, my name is Ali and I ordered a laptop.",
    "Can I get it delivered to Lahore?",
    "What is my name and what did I order?",
]

for question in questions:
    messages.append({"role": "user", "content": question})

    response = client.messages.create(
        model=MODEL,
        max_tokens=300,
        system=SYSTEM,
        messages=messages,
    )
    reply = response.content[0].text

    messages.append({"role": "assistant", "content": reply})

    print(f"You: {question}")
    print(f"AI:  {reply}")
    print(f"     [input tokens: {response.usage.input_tokens}]\n")

count = client.messages.count_tokens(model=MODEL, system=SYSTEM, messages=messages)
print("Tokens in the full conversation:", count.input_tokens)
```

| OpenAI Chat Completions | Anthropic Messages |
|---|---|
| System prompt inside `messages` | `system=` parameter |
| `max_tokens` optional | `max_tokens` required |
| `response.choices[0].message.content` | `response.content[0].text` |
| `response.usage.prompt_tokens` | `response.usage.input_tokens` |

`messages.count_tokens(...)` tells you how many tokens a conversation uses **before** you send it, so you can trim in time.

## 11. Example 4: Server-Side Memory (OpenAI and Gemini)

Some providers can store the conversation **for you**. You send only the new message plus an ID.

**OpenAI Responses API** (`previous_response_id`):

```python
from dotenv import load_dotenv
from openai import OpenAI

load_dotenv()
client = OpenAI()

first = client.responses.create(
    model="gpt-5.5",
    input="Hi, my name is Ali and I ordered a laptop.",
)

second = client.responses.create(
    model="gpt-5.5",
    previous_response_id=first.id,
    input="What is my name and what did I order?",
)

print(second.output_text)
```

**Gemini Interactions API** (`previous_interaction_id`, requires `uv add google-genai` and `GEMINI_API_KEY`):

```python
from dotenv import load_dotenv
from google import genai

load_dotenv()
client = genai.Client()

first = client.interactions.create(
    model="gemini-3.8-flash",
    input="Hi, my name is Ali and I ordered a laptop.",
)

second = client.interactions.create(
    model="gemini-3.8-flash",
    input="What is my name and what did I order?",
    previous_interaction_id=first.id,
)

print(second.output_text)
```

| | Client-side memory (Examples 1–3) | Server-side memory (Example 4) |
|---|---|---|
| Who stores history | Your code | The provider |
| Works with any provider | Yes | Only providers that support it |
| Data retention | You decide | Provider rules (OpenAI keeps responses 30 days by default; Gemini keeps interactions 55 days on paid tier, 1 day on free tier) |
| You still pay for history tokens | Yes | Yes, previous turns still count as input tokens |

> **Mental Model: Your Notebook vs the Hotel Locker**
> Client-side memory is your own notebook: you carry it and control it. Server-side memory is a hotel locker: convenient, but someone else holds the key and decides how long to keep it.

## 12. Example 5: LangChain (Message List)

The simplest LangChain memory is the same idea: keep a list of messages.

Create `memory_langchain.py`:

```python
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

llm = ChatOllama(model="gemma4:e2b", temperature=0, num_ctx=8192)

messages = [SystemMessage("You are a friendly support assistant. Keep answers short.")]

questions = [
    "Hi, my name is Ali and I ordered a laptop.",
    "Can I get it delivered to Lahore?",
    "What is my name and what did I order?",
]

for question in questions:
    messages.append(HumanMessage(question))
    response = llm.invoke(messages)
    messages.append(response)

    print(f"You: {question}")
    print(f"AI:  {response.content}\n")
```

| Code | Meaning |
|---|---|
| `SystemMessage`, `HumanMessage` | LangChain's message classes for the system and user roles |
| `llm.invoke(messages)` | Send the whole conversation |
| `messages.append(response)` | The reply is already an `AIMessage`, so it can be stored directly |
| `num_ctx=8192` | Ollama context length, same as `options={"num_ctx": ...}` in Example 1 |

To use Claude or GPT instead, swap `ChatOllama` for `ChatAnthropic` (`uv add langchain-anthropic`) or `ChatOpenAI` (`uv add langchain-openai`). The rest of the code stays the same.

## 13. Example 6: LangChain Token Trimming

`trim_messages` keeps the newest messages that fit a **token budget**, and always keeps the system prompt.

Create `memory_trim.py`:

```python
from langchain_core.messages import AIMessage, HumanMessage, SystemMessage
from langchain_core.messages.utils import count_tokens_approximately, trim_messages
from langchain_ollama import ChatOllama

llm = ChatOllama(model="gemma4:e2b", temperature=0)

history = [
    SystemMessage("You are a friendly support assistant. Keep answers short."),
    HumanMessage("Hi, my name is Ali and I ordered a laptop."),
    AIMessage("Hello Ali! Thanks for your laptop order. How can I help?"),
    HumanMessage("Can I get it delivered to Lahore?"),
    AIMessage("Yes, we deliver to Lahore within 3 to 5 working days."),
    HumanMessage("Do you offer a warranty?"),
    AIMessage("Yes, every laptop has a one-year warranty."),
    HumanMessage("What is my name and what did I order?"),
]

trimmed = trim_messages(
    history,
    strategy="last",
    token_counter=count_tokens_approximately,
    max_tokens=80,
    start_on="human",
    include_system=True,
)

print("Before:", count_tokens_approximately(history), "tokens,", len(history), "messages")
print("After: ", count_tokens_approximately(trimmed), "tokens,", len(trimmed), "messages\n")

for message in trimmed:
    print(f"  {message.type}: {message.content}")

print("\nAI:", llm.invoke(trimmed).content)
```

| Parameter | Meaning |
|---|---|
| `strategy="last"` | Keep the most recent messages |
| `token_counter=count_tokens_approximately` | A fast estimate; you can also pass the model itself for exact counts |
| `max_tokens=80` | The token budget for the history |
| `start_on="human"` | The kept history must start with a user message (most providers require this) |
| `include_system=True` | Always keep the system prompt |

With `max_tokens=80`, the history drops from 8 messages (about 126 tokens) to 4 messages (about 59 tokens). The kept messages are the system prompt, the warranty question and answer, and the final question. The introduction is gone, so the model **cannot** say Ali's name or what he ordered.

**Experiment:** change `max_tokens` to 40, 80, and 200. At 40 and 80, the introduction is trimmed away. At 200, everything fits and the model answers correctly. This is the trade-off between cost and memory.

## 14. Example 7: LangChain Persistence with LangGraph Checkpointer

This is the **current official** way to give a LangChain chat app memory. It is **not an agent**: it is a one-step graph that simply calls the model. The checkpointer saves each conversation under a `thread_id`, so many users can chat at the same time without mixing their histories.

Create `memory_langgraph.py`:

```python
from langchain_ollama import ChatOllama
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import START, MessagesState, StateGraph

llm = ChatOllama(model="gemma4:e2b", temperature=0)


def call_model(state: MessagesState):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}


builder = StateGraph(MessagesState)
builder.add_node("call_model", call_model)
builder.add_edge(START, "call_model")
chatbot = builder.compile(checkpointer=InMemorySaver())


def ask(question: str, thread_id: str) -> str:
    config = {"configurable": {"thread_id": thread_id}}
    result = chatbot.invoke({"messages": [{"role": "user", "content": question}]}, config)
    return result["messages"][-1].content


print("Ali: ", ask("Hi, my name is Ali and I ordered a laptop.", thread_id="ali"))
print("Sara:", ask("Hi, my name is Sara and I ordered a phone.", thread_id="sara"))
print("Ali: ", ask("What is my name and what did I order?", thread_id="ali"))
print("Sara:", ask("What is my name and what did I order?", thread_id="sara"))
```

**What to notice:** you only send the **new** message. The checkpointer stores and reloads the history for each thread, and Ali and Sara never see each other's conversations.

| Code | Meaning |
|---|---|
| `MessagesState` | A ready-made state that holds a list of messages and appends new ones |
| `call_model` | The single step: send the history to the model, return its reply |
| `InMemorySaver()` | Stores conversations in RAM (lost when the program stops) |
| `thread_id` | One ID per conversation, like a chat session ID |

In production, replace `InMemorySaver` with a database-backed checkpointer such as `PostgresSaver` (from `langgraph-checkpoint-postgres`), so conversations survive restarts.

> **Mental Model: The Filing Cabinet**
> The checkpointer is a filing cabinet with one folder per `thread_id`. Before each answer, the right folder is pulled out; after each answer, the new page is filed back in.

## 15. Which Approach Should You Use?

| Situation | Recommended approach |
|---|---|
| Learning, scripts, one user | Plain message list (Examples 1, 3, 5) |
| Long chats on small local models | Token trimming (Example 6) |
| Multi-user chat app with LangChain | LangGraph checkpointer (Example 7) |
| Quick prototype on one provider | Server-side state (Example 4) |
| Remember users across conversations | Long-term memory (later modules) |

---

## Key Takeaways

1. The **context window** is the token limit for input plus output in one request.
2. **LLMs are stateless.** Chat "memory" means your app resends the conversation every turn.
3. Context windows grew from **2K tokens (2020) to about 1M tokens (2026)**, but longer context costs more, runs slower, and can reduce quality.
4. Ollama's **default** context is often only **4K tokens** on laptops; set `num_ctx` when you need more.
5. Core strategies: **full history, sliding window, token trimming, summarization, server-side state, and persistence**.
6. In LangChain 1.x, use a **message list**, **`trim_messages`**, or a **LangGraph checkpointer**. Old memory classes are deprecated.

**Practice:** Combine Examples 6 and 7. Inside `call_model`, trim `state["messages"]` with `trim_messages` before calling the model, so each thread keeps its full history in the checkpointer but only sends a token-limited window to the model.
