### 2.4 Limits: Hallucination, Knowledge Cutoff, Cost, and Latency

---

## 1. Why Limits Matter

LLMs are powerful, but every production GenAI system is designed **around their limits**. Four limits matter most:

| Limit | The problem | The engineering question |
|---|---|---|
| **Hallucination** | The model can state false things confidently | How do we keep answers grounded and checkable? |
| **Knowledge cutoff** | The model doesn't know recent events | How do we give it current information? |
| **Cost** | Every token costs money | How do we keep the bill predictable? |
| **Latency** | Answers take time | How do we make the app feel fast? |

> **Mental Model: The Brilliant New Intern**
> An LLM is a brilliant intern who read a huge library up to a certain date. They write fast and sound confident, but they sometimes guess, don't know this week's news, charge by the word, and need a moment to think. Your job is to **give them the right documents, check their work, and set a budget**.

---

## 2. Hallucination

**A hallucination is an answer that sounds correct but is false or made up.**

### Why It Happens

From Lesson 2.3: the model picks the **most likely next token**, not the **true** one. When it doesn't know something, the most likely-sounding answer is often a confident guess. There is no built-in "fact check" step.

### Common Types

| Type | Example |
|---|---|
| Invented facts | A wrong date, statistic, or price |
| Fake sources | Citations, URLs, or court cases that don't exist |
| Wrong reasoning | Correct-looking steps that reach a wrong answer |
| Ignoring the given context | Answering from memory instead of the document you provided |
| Overconfident "yes" | Agreeing with a false assumption in the question |

### Real-World Consequences

| Year | Case | Lesson |
|---|---|---|
| 2023 | US lawyers submitted a court brief with case citations invented by ChatGPT (*Mata v. Avianca*) and were sanctioned | Never trust citations without checking them |
| 2024 | Air Canada was held responsible when its website chatbot gave a customer wrong refund policy information (*Moffatt v. Air Canada*) | Companies are responsible for what their chatbot says |

### How Engineers Reduce Hallucination

| Technique | How it helps |
|---|---|
| **Grounding** | Give the model the facts (documents, database results) and tell it to answer only from them |
| **Permission to say "I don't know"** | Removes the pressure to guess |
| **Low temperature** | Makes the model stick to its most likely answer (Lesson 2.3) |
| **Structured output** | Forces fields like `found_in_context: bool`, so the app can detect "no answer" |
| **Verification** | Check important facts with code, a database, or a human |
| **RAG** | Automatically retrieves relevant documents for grounding (later module) |

> **Mental Model: Open-Book vs Closed-Book Exam**
> Without grounding, the model takes a **closed-book exam** from memory and guesses when unsure. With grounding, it takes an **open-book exam** with the right pages in front of it. Most production GenAI turns closed-book questions into open-book ones.

## 3. Knowledge Cutoff

**The knowledge cutoff is the date after which the model has no training data.** The model does not know anything that happened later, and it does not know today's date unless you tell it.

| Model | Knowledge cutoff |
|---|---|
| Claude Opus 5.5, Claude Sonnet 5.5 | June 2026 |
| Claude Haiku 4.5 | February 2025 |
| Other models | Listed on each provider's model page or model card |

### What This Means in Practice

| Question | Risk |
|---|---|
| "What is today's date?" | The model may guess a date near its cutoff |
| "What is the latest version of Python?" | It may name an older version |
| "What is our current refund policy?" | It never knew your company's private data |

### How Engineers Handle It

| Technique | Use when |
|---|---|
| Put **today's date** in the system prompt | Always; it's cheap and prevents date mistakes |
| Pass **current data** in the prompt (prices, policies, news) | The answer depends on recent or private facts |
| Use **web search or RAG** | The information changes often (later modules) |

> **Mental Model: The Traveller Back From a Long Trip**
> The model is like someone who has been away for months with no internet. They know a lot, but not the latest news. Tell them today's date and hand them the newspaper before asking about current events.

## 4. Cost

From Lesson 2.1: providers charge per **input token** and per **output token**, and output usually costs **about 5 times more** than input.

### Price Snapshot (October 2026, per 1 million tokens)

| Model | Input | Output |
|---|---|---|
| OpenAI gpt-6-luna (small) | $0.05 | $0.25 |
| OpenAI gpt-6.1-sol | $1.00 | $5.00 |
| Claude Haiku 4.5 | $1.00 | $5.00 |
| Claude Sonnet 5.5 | $2.00 | $10.00 |
| Claude Opus 5.5 | $4.00 | $20.00 |
| OpenAI gpt-6-astra (flagship) | $5.00 | $25.00 |
| Local model via Ollama | $0 | $0 (you pay for hardware and electricity) |

Prices change often. Always check the provider's pricing page before estimating.

**The same task can cost 100 times more on a flagship model than on a small one.**

### How Engineers Control Cost

| Technique | Saving |
|---|---|
| Use the **smallest model that does the job well** | Often the biggest saving |
| Keep prompts and history short (Lesson 2.2) | Fewer input tokens every turn |
| Set `max_tokens` and ask for short answers (Lesson 2.3) | Fewer output tokens |
| **Prompt caching** (repeated long system prompts or documents) | Cached input is billed at about 5–10% of the normal price on OpenAI and Anthropic |
| **Batch API** for jobs that don't need an instant answer | Anthropic offers 50% off; other providers offer similar discounts |
| **Track usage** on every request | You can't control what you don't measure |

> **Mental Model: The Taxi, the Bus, and the Bicycle**
> A flagship model is a taxi: fast and comfortable, but expensive for every trip. A small model is a bus: cheap and fine for most routes. A local model is a bicycle: free to ride, but you bought the bicycle. Pick the vehicle for the trip.

## 5. Latency

**Latency is how long the user waits.** Two numbers matter:

| Metric | Meaning | Why it matters |
|---|---|---|
| **Time to first token (TTFT)** | Seconds until the first word appears | How fast the app **feels** |
| **Tokens per second** | Speed of writing after the first token | How long the full answer takes |

**Total time ≈ TTFT + (output tokens ÷ tokens per second)**

### What Makes Latency Worse

| Cause | Why |
|---|---|
| Long prompts and history | More input to read before the first token |
| Long answers | More tokens to generate one by one |
| Larger models | More computation per token |
| Reasoning models | They "think" (generate hidden tokens) before answering |
| Small local hardware | Laptops generate fewer tokens per second than data center GPUs |

### How Engineers Reduce Latency

| Technique | Effect |
|---|---|
| **Streaming** (Lesson 1.2) | Same total time, but the user sees text almost immediately |
| Smaller or faster models | Lower TTFT and more tokens per second |
| Shorter prompts and `max_tokens` | Less to read and less to write |
| Prompt caching | Repeated input is processed faster |
| **Timeouts and retries** | The app doesn't hang forever on a slow or failed request |

> **Mental Model: The Restaurant**
> TTFT is how long until the first dish arrives. Tokens per second is how fast the rest of the meal comes. Streaming is serving dishes as they're ready instead of bringing the whole meal at once.

---

## 6. The Trade-Off Triangle

| You want more... | You usually pay with... |
|---|---|
| **Quality** (bigger model, more context, reasoning) | More cost and more latency |
| **Speed** (smaller model, shorter output) | Some quality |
| **Low cost** (small or local model, caching, batching) | Some quality or speed |

Good engineering means choosing the **right balance for each task**, not the biggest model for everything.

## 8. OpenAI Python SDK Examples

### Example 1: Test for Hallucination

Ask about something that **does not exist**, with and without permission to say "I don't know."

Create `hallucination_test.py`:

```python
from llm import get_client

client, model = get_client()

QUESTION = "Summarize the main points of the 2019 Lahore Quantum Computing Treaty."

SYSTEM_PROMPTS = {
    "Default": "You are a helpful assistant.",
    "Honest": (
        "You are a helpful assistant. If you are not sure something exists or is true, "
        "say 'I don't know' instead of guessing. Never invent facts, names, or sources."
    ),
}

for label, system_prompt in SYSTEM_PROMPTS.items():
    response = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": QUESTION},
        ],
        temperature=0,
        max_tokens=150,
    )
    print(f"--- {label} ---")
    print(response.choices[0].message.content, "\n")
```

**What to notice:** the treaty is invented. Small models often describe it in confident detail under the default prompt. The honest prompt usually reduces this, but **does not fully prevent it**. Prompting alone is not enough, which is why grounding matters.

### Example 2: Grounding with Provided Context

Create `grounded_answer.py`:

```python
from llm import get_client

client, model = get_client()

POLICY = """
Refund policy (ShopPK):
- Refunds are accepted within 14 days of delivery.
- Items must be unused and in original packaging.
- Electronics have a 7-day refund window.
- Refunds are paid to the original payment method within 5 working days.
"""

SYSTEM = (
    "You are a support assistant. Answer ONLY using the policy below. "
    "If the answer is not in the policy, reply exactly: "
    "'I don't have that information. Please contact support.'\n\n"
    f"POLICY:\n{POLICY}"
)

questions = [
    "Can I return a laptop after 10 days?",
    "How long does it take to get my money back?",
    "Do you offer free international shipping?",
]

for question in questions:
    response = client.chat.completions.create(
        model=model,
        messages=[{"role": "system", "content": SYSTEM}, {"role": "user", "content": question}],
        temperature=0,
        max_tokens=100,
    )
    print(f"Q: {question}")
    print(f"A: {response.choices[0].message.content}\n")
```

**What to notice:** the laptop question is answered from the 7-day electronics rule. The shipping question is not in the policy, so the correct answer is the fallback message, not a guess.

### Example 3: Knowledge Cutoff and Today's Date

Create `knowledge_cutoff.py`:

```python
from datetime import date

from llm import get_client

client, model = get_client()

QUESTION = "What is today's date, and how many days are left until the end of this year?"


def ask(system_prompt: str) -> str:
    response = client.chat.completions.create(
        model=model,
        messages=[{"role": "system", "content": system_prompt}, {"role": "user", "content": QUESTION}],
        temperature=0,
        max_tokens=100,
    )
    return response.choices[0].message.content


print("Without date:\n", ask("You are a helpful assistant."), "\n")

today = date.today()
print("With date:\n", ask(f"You are a helpful assistant. Today's date is {today:%A, %d %B %Y}."))

days_left = (date(today.year, 12, 31) - today).days
print(f"\nChecked with Python: {days_left} days left.")
```

**What to notice:** without the date, the model guesses (often a date near its training cutoff). With the date, it answers correctly. The final line uses **Python to verify the arithmetic**. Use code, not the model, for exact calculations.

### Example 4: Cost Tracker

Create `cost_tracker.py`:

```python
from llm import get_client

client, model = get_client()

# USD per 1 million tokens (October 2026 snapshot; check pricing pages before use)
PRICES = {
    "gpt-6-luna": {"input": 0.05, "output": 0.25},
    "claude-haiku-4-5": {"input": 1.00, "output": 5.00},
    "claude-opus-5-5": {"input": 4.00, "output": 20.00},
}


def cost_usd(input_tokens: int, output_tokens: int, model_name: str) -> float:
    price = PRICES[model_name]
    return (input_tokens * price["input"] + output_tokens * price["output"]) / 1_000_000


response = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "Write a 100-word product description for a school backpack."}],
    max_tokens=200,
)

usage = response.usage
print(f"Input: {usage.prompt_tokens} tokens, output: {usage.completion_tokens} tokens\n")

for model_name in PRICES:
    one = cost_usd(usage.prompt_tokens, usage.completion_tokens, model_name)
    print(f"{model_name:<18} 1 request: ${one:.6f}   100,000 requests: ${one * 100_000:,.2f}")
```

**What to notice:** the same request, priced on three models, shows how much model choice matters at scale. The token counts come from your real request; the prices are the snapshot table.

### Example 5: Measure Latency with Streaming

Create `latency.py`:

```python
import time

from llm import get_client

client, model = get_client()

messages = [{"role": "user", "content": "Explain what latency means for a chatbot in 5 sentences."}]

start = time.perf_counter()
first_token_time = None
output_tokens = 0

stream = client.chat.completions.create(
    model=model,
    messages=messages,
    max_tokens=200,
    stream=True,
    stream_options={"include_usage": True},
)

for chunk in stream:
    if chunk.choices and chunk.choices[0].delta.content:
        if first_token_time is None:
            first_token_time = time.perf_counter()
        print(chunk.choices[0].delta.content, end="", flush=True)
    if chunk.usage:
        output_tokens = chunk.usage.completion_tokens

end = time.perf_counter()
ttft = first_token_time - start
generation_time = end - first_token_time

print("\n")
print(f"Time to first token: {ttft:.2f} s")
print(f"Total time:          {end - start:.2f} s")
print(f"Output tokens:       {output_tokens}")
print(f"Tokens per second:   {output_tokens / generation_time:.1f}")
```

| Code | Meaning |
|---|---|
| `time.perf_counter()` | A precise timer for measuring durations |
| `stream_options={"include_usage": True}` | Ask for token usage in the final streamed chunk |
| `first_token_time - start` | Time to first token (TTFT) |

**Experiment:** run it with `gemma4:e2b`, then with a cloud model (`PROVIDER=gemini`), and compare TTFT and tokens per second.

## 9. LangChain Examples

### Example 6: Grounded Answers with Structured Output

Structured output lets the **app** know when the model could not find the answer, instead of hoping the text says so.

Create `lc_grounded.py`:

```python
from langchain_core.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama
from pydantic import BaseModel, Field


class GroundedAnswer(BaseModel):
    found_in_context: bool = Field(description="True only if the policy contains the answer")
    answer: str = Field(description="The answer, or an empty string if not found")
    quote: str = Field(description="The exact policy line used, or an empty string")


POLICY = """
- Refunds are accepted within 14 days of delivery.
- Electronics have a 7-day refund window.
- Refunds are paid within 5 working days.
"""

llm = ChatOllama(model="gemma4:e2b", temperature=0)
grounded_llm = llm.with_structured_output(GroundedAnswer)

SYSTEM = SystemMessage(f"Answer only from this policy. Do not guess.\n\nPOLICY:\n{POLICY}")

for question in ["Can I return a phone after 10 days?", "Do you deliver to Dubai?"]:
    result = grounded_llm.invoke([SYSTEM, HumanMessage(question)])
    if result.found_in_context:
        print(f"{question}\n  Answer: {result.answer}\n  Source: {result.quote}\n")
    else:
        print(f"{question}\n  Not in policy. Escalating to a human agent.\n")
```

| Code | Meaning |
|---|---|
| `with_structured_output(GroundedAnswer)` | The model must return a `GroundedAnswer` object (Lesson 1.3) |
| `found_in_context` | Your code, not the model's wording, decides what to do next |
| `quote` | Asking for the source line makes answers easier to check |

### Example 7: Knowledge Cutoff in LangChain

Create `lc_cutoff.py`:

```python
from datetime import date

from langchain_core.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

llm = ChatOllama(model="gemma4:e2b", temperature=0)

today = date.today()
system = SystemMessage(
    f"Today's date is {today:%d %B %Y}. "
    "Your training data may be older than today. "
    "If a question depends on recent events you don't know about, say so clearly."
)

question = HumanMessage("Which is the newest Python version, and is it safe to use in production?")

print(llm.invoke([system, question]).content)
```

**What to notice:** the model can't know the newest release after its cutoff, but with this system prompt it should **say that its information may be outdated** instead of presenting an old version as the latest.

### Example 8: Track Tokens and Cost Across Many Calls

LangChain's `get_usage_metadata_callback` adds up token usage for every model call inside a `with` block.

Create `lc_cost.py`:

```python
from langchain_core.callbacks import get_usage_metadata_callback
from langchain_ollama import ChatOllama

llm = ChatOllama(model="gemma4:e2b", temperature=0.3, num_predict=100)

PRICE_PER_MILLION = {"input": 1.00, "output": 5.00}  # what this usage would cost on a Haiku-class cloud model

questions = [
    "What is a token?",
    "What is a context window?",
    "What is temperature in LLMs?",
]

with get_usage_metadata_callback() as tracker:
    for question in questions:
        llm.invoke(question)

for model_name, usage in tracker.usage_metadata.items():
    cost = (
        usage["input_tokens"] * PRICE_PER_MILLION["input"]
        + usage["output_tokens"] * PRICE_PER_MILLION["output"]
    ) / 1_000_000
    print(f"Model: {model_name}")
    print(f"  Input tokens:  {usage['input_tokens']}")
    print(f"  Output tokens: {usage['output_tokens']}")
    print(f"  Cloud-equivalent cost: ${cost:.6f}")
```

| Code | Meaning |
|---|---|
| `with get_usage_metadata_callback() as tracker:` | Start counting tokens for all calls inside the block |
| `tracker.usage_metadata` | A dictionary of total usage per model name |

### Example 9: Streaming Latency, Timeouts, and Retries

Create `lc_latency.py`:

```python
import time

from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="gemma4:e2b",
    base_url="http://localhost:11434/v1/",
    api_key="ollama",
    temperature=0.3,
    max_tokens=150,
    timeout=30,      # give up after 30 seconds
    max_retries=2,   # retry failed requests up to 2 times
)

start = time.perf_counter()
first_token_time = None

for chunk in llm.stream("Give 3 tips to make a chatbot respond faster."):
    if chunk.content and first_token_time is None:
        first_token_time = time.perf_counter()
    print(chunk.content, end="", flush=True)

end = time.perf_counter()
print(f"\n\nTime to first token: {first_token_time - start:.2f} s")
print(f"Total time:          {end - start:.2f} s")
```

| Setting | Why it matters |
|---|---|
| `llm.stream(...)` | Shows text as soon as the first token arrives |
| `timeout=30` | The app fails fast instead of hanging on a slow request |
| `max_retries=2` | Network errors, rate limits (429), and server errors (5xx) are retried automatically |

### Example 10: Protect Your Budget with a Rate Limiter

A bug in a loop can send thousands of requests in seconds. LangChain's `InMemoryRateLimiter` caps how fast requests are sent.

Create `lc_rate_limit.py`:

```python
import time

from langchain.rate_limiters import InMemoryRateLimiter
from langchain_ollama import ChatOllama

rate_limiter = InMemoryRateLimiter(
    requests_per_second=0.5,   # at most 1 request every 2 seconds
    check_every_n_seconds=0.1,
    max_bucket_size=1,         # no bursts
)

llm = ChatOllama(model="gemma4:e2b", temperature=0, num_predict=20, rate_limiter=rate_limiter)

start = time.perf_counter()
for number in range(1, 4):
    reply = llm.invoke(f"Say the number {number} in Urdu, one word only.")
    print(f"{time.perf_counter() - start:5.1f} s  {reply.content.strip()}")
```

**What to notice:** the requests are spaced about 2 seconds apart, even though the loop runs as fast as it can. The limiter controls the **number** of requests, not their size, so combine it with `max_tokens` and usage tracking.

## 10. Production Checklist

| Limit | Minimum practice in every GenAI app |
|---|---|
| Hallucination | Ground answers in provided data, allow "I don't know", use temperature 0 for facts, verify important outputs |
| Knowledge cutoff | Put today's date in the system prompt; pass current data instead of relying on memory |
| Cost | Choose the smallest suitable model, set `max_tokens`, track usage per request |
| Latency | Stream responses, keep prompts short, set timeouts and retries |

---

## Key Takeaways

1. **Hallucination** happens because models predict likely tokens, not true facts. Reduce it with grounding, honest prompts, low temperature, structured output, and verification.
2. The **knowledge cutoff** means the model doesn't know recent events or today's date. Always pass the date and current data.
3. **Cost** depends on tokens and model choice; prices can differ by **100 times** between models. Measure every request.
4. **Latency** has two parts: time to first token and tokens per second. Streaming, smaller models, and shorter prompts all help.
5. Every design choice is a **trade-off between quality, speed, and cost**.
