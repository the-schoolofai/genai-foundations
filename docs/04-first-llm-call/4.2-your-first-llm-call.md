## Module 4: Python Setup and Your First API Call

### 4.2 Your First LLM Call: Messages In, a Message Out

---

## 1. The One Rule of Chat Models

Every LangChain chat model, for every provider, follows the same contract:

```text
messages in  --->  [ chat model ]  --->  one AIMessage out
```

Once you understand what goes **in** and what comes **out**, you can work with any model.

> **Mental Model: The Post Office**
> You post a bundle of letters (the messages). The post office (the model) sends back **one reply letter in an envelope**. The letter is the text; the envelope carries the stamps: who sent it, how much postage it cost, and why it stopped writing.

---

## 2. What Goes In: Three Input Forms

`llm.invoke(...)` accepts three forms. LangChain converts all of them into messages.

| Form | Example | Use when |
|---|---|---|
| **String** | `llm.invoke("What is Python?")` | A single question with no rules |
| **List of dictionaries** | `[{"role": "user", "content": "..."}]` | Sharing code with the OpenAI SDK style |
| **List of message objects** | `[SystemMessage("..."), HumanMessage("...")]` | Most LangChain code |

A string is simply turned into one user message.

### The Message Classes

| Class | Role | Who writes it |
|---|---|---|
| `SystemMessage` | `system` | You, the developer: rules and persona |
| `HumanMessage` | `user` | The person using the app |
| `AIMessage` | `assistant` | The model's replies |
| `ToolMessage` | `tool` | Results from your functions (Lesson 4.5) |

Import them with `from langchain.messages import SystemMessage, HumanMessage, AIMessage`.

---

## 3. What Comes Out: Anatomy of an `AIMessage`

| Attribute | What it holds | Example |
|---|---|---|
| `.text` | The reply as a plain string | `"Python is a popular language."` |
| `.content` | The raw content: a string **or** a list of blocks | Depends on the provider |
| `.content_blocks` | The content in LangChain's **standard** format | `[{"type": "text", "text": "..."}]` |
| `.usage_metadata` | Token counts | `{"input_tokens": 20, "output_tokens": 7, "total_tokens": 27}` |
| `.response_metadata` | Provider details: model name, provider, finish reason | `{"model_name": "gemma3:1b", ...}` |
| `.id` | A unique ID for this message | `"lc_run--01a1..."` |
| `.tool_calls` | Functions the model wants to call (Lesson 4.5) | `[]` |

> **Mental Model: The Letter and the Envelope**
> `.text` is the letter. `.usage_metadata` is the postage. `.response_metadata` is the stamps. `.content_blocks` is the same letter, sorted into labelled sections.

---

## 4. `.text` vs `.content` vs `.content_blocks`

This matters as soon as you switch providers.

| Attribute | Always a string? | Use it for |
|---|---|---|
| `.content` | **No.** Some providers return a **list** (for example, reasoning plus text) | Low-level, provider-specific work |
| `.text` | **Yes.** Only the answer text | Printing and saving replies (use this by default) |
| `.content_blocks` | No, always a list of **standard** blocks | Reading reasoning, citations, images in one format |

A model that "thinks" (Lesson 3.4) may return content like this:

```python
[
    {"type": "thinking", "thinking": "The user wants a short definition."},
    {"type": "text", "text": "Python is a popular programming language."},
]
```

If your code did `print(reply.content)`, it would print the whole list. `reply.text` gives just the answer, and `reply.content_blocks` labels each part as `reasoning` or `text` in the same format for every provider.

**Rule:** use `.text` for the answer, and `.content_blocks` when you need the other parts.

---

## 5. Provider Differences in `response_metadata`

The **same idea** can have **different names** across providers. For example, the reason the model stopped writing:

| Provider | Key | Example value |
|---|---|---|
| Ollama | `done_reason` | `"stop"` |
| OpenAI, Gemini | `finish_reason` | `"stop"` / `"STOP"` |
| Anthropic | `stop_reason` | `"end_turn"` |

`model_name` and `model_provider` are set by LangChain for every provider. For anything else, write a small helper that checks the possible names, as in Example 2.

---

## 6. Model Profiles: What Can This Model Do?

LangChain chat models expose a **`.profile`**: a dictionary of capabilities, mostly from the open-source models.dev project.

```python
llm.profile
# {"max_input_tokens": 1048576, "image_inputs": True, "tool_calling": True, ...}
```

| Field | Use it to... |
|---|---|
| `max_input_tokens` | Know the context window (Lesson 2.2) |
| `max_output_tokens` | Know the longest possible answer |
| `image_inputs` | Decide whether to allow image uploads |
| `tool_calling` | Check the model can use tools (Lesson 4.5) |
| `structured_output` | Check native structured output support |
| `reasoning_output` | Check whether the model can return reasoning |

Profiles can be **missing** (`None` or empty), especially for local Ollama models and very new releases. Always use `llm.profile or {}`.

> **Mental Model: The Spec Sheet**
> A profile is the spec sheet on the box: screen size, battery, ports. Your app reads it before deciding which features to switch on.

## 7. Calling Patterns

| Method | Does | Lesson |
|---|---|---|
| `invoke(input)` | One request, wait for the full reply | This lesson |
| `batch([input1, input2, ...])` | Many requests in parallel, a list of replies back | This lesson |
| `stream(input)` | One request, reply arrives in chunks | 4.4 |
| `ainvoke`, `abatch`, `astream` | Async versions for web servers | Later modules |

## 8. Examples

These use the `cue-chat` project and `config.py` from Lesson 4.1. Every script was run and its output checked (see Section 9).

### Example 1: Three Input Forms

Create `first_call.py`:

```python
from langchain.messages import HumanMessage, SystemMessage

from config import get_llm

llm = get_llm()

# 1. A plain string: becomes one user message
reply = llm.invoke("In one sentence, what is Python?")
print("1.", reply.text)

# 2. A list of dictionaries: the OpenAI-style format
reply = llm.invoke([
    {"role": "system", "content": "You are a friendly teacher. Answer in one sentence."},
    {"role": "user", "content": "What is Python?"},
])
print("2.", reply.text)

# 3. A list of message objects: the LangChain format
reply = llm.invoke([
    SystemMessage("You are a friendly teacher. Answer in one sentence."),
    HumanMessage("What is Python?"),
])
print("3.", reply.text)
```

```bash
uv run first_call.py
```

**What to notice:** forms 2 and 3 send exactly the same messages; choose one style and use it consistently.

### Example 2: Inspect Everything in the Reply

Create `inspect_reply.py`:

```python
from config import get_llm

llm = get_llm()
reply = llm.invoke("Name three uses of Python, comma separated.")


def finish_reason(message) -> str:
    """Providers use different names for the same idea."""
    metadata = message.response_metadata
    return metadata.get("finish_reason") or metadata.get("done_reason") or metadata.get("stop_reason") or "unknown"


print("Class:         ", type(reply).__name__)
print("Text:          ", reply.text)
print("Content type:  ", type(reply.content).__name__)
print("Content blocks:", reply.content_blocks)
print("Tokens:        ", reply.usage_metadata)
print("Model:         ", reply.response_metadata.get("model_name"))
print("Provider:      ", reply.response_metadata.get("model_provider"))
print("Finish reason: ", finish_reason(reply))
print("Message ID:    ", reply.id)
```

Example output with `ollama:gemma3:1b` (every line's format was tested; your reply text, token counts, and ID will differ):

```text
Class:          AIMessage
Text:           Web development, data analysis, automation.
Content type:   str
Content blocks: [{'type': 'text', 'text': 'Web development, data analysis, automation.'}]
Tokens:         {'input_tokens': 20, 'output_tokens': 7, 'total_tokens': 27}
Model:          gemma3:1b
Provider:       ollama
Finish reason:  stop
Message ID:     lc_run--01a12703-4c9f-70c1-8341-9e2c058378bb-0
```

Switch `.env` to Gemini and run it again: the class is the same, `Provider` changes, and `Content type` may change.

### Example 3: Why `.text` Is Safer than `.content`

This example needs **no model**: it builds the kind of reply a reasoning model returns, so you can see the difference.

Create `content_blocks_demo.py`:

```python
from langchain.messages import AIMessage

# What a reply from a model that "thinks" can look like (Anthropic format)
reply = AIMessage(
    content=[
        {"type": "thinking", "thinking": "The user wants a short definition.", "signature": "abc123"},
        {"type": "text", "text": "Python is a popular programming language."},
    ],
    response_metadata={"model_provider": "anthropic"},
)

print("content is a:", type(reply.content).__name__)
print()
print(".text          ->", reply.text)
print()
for block in reply.content_blocks:
    print(".content_blocks ->", block["type"], ":", block.get("text") or block.get("reasoning"))
```

Tested output:

```text
content is a: list

.text          -> Python is a popular programming language.

.content_blocks -> reasoning : The user wants a short definition.
.content_blocks -> text : Python is a popular programming language.
```

**What to notice:** the provider called it `thinking`; `content_blocks` converted it to the standard `reasoning` type. Your code reads one format, whichever provider you use.

### Example 4: Read the Model Profile

Create `profile_check.py`:

```python
from config import get_llm

llm = get_llm()
profile = llm.profile or {}

if not profile:
    print("No profile data for this model (common for local or very new models).")
else:
    for key in ["max_input_tokens", "max_output_tokens", "image_inputs", "tool_calling", "structured_output", "reasoning_output"]:
        print(f"{key:<18} {profile.get(key)}")

if profile.get("image_inputs"):
    print("\nThis model can read images.")
```

Tested output with `ollama:gemma3:1b`:

```text
No profile data for this model (common for local or very new models).
```

Tested output with `google_genai:gemini-3.5-flash-lite`:

```text
max_input_tokens   1048576
max_output_tokens  65536
image_inputs       True
tool_calling       True
structured_output  True
reasoning_output   True

This model can read images.
```

Reading the profile does not call the model, so it costs nothing.

### Example 5: Many Questions at Once with `batch`

Create `batch_demo.py`:

```python
import time

from config import get_llm

llm = get_llm(temperature=0)

questions = [
    "In five words, what is Python?",
    "In five words, what is an API?",
    "In five words, what is an LLM?",
]

start = time.perf_counter()
replies = llm.batch(questions, config={"max_concurrency": 3})
print(f"Answered {len(replies)} questions in {time.perf_counter() - start:.2f} s\n")

for question, reply in zip(questions, replies):
    print(f"Q: {question}\nA: {reply.text}\n")
```

| Code | Meaning |
|---|---|
| `get_llm(temperature=0)` | Overrides the `.env` temperature for this script (Lesson 4.1) |
| `llm.batch(questions, ...)` | Sends all questions in parallel; replies come back **in the same order** |
| `config={"max_concurrency": 3}` | At most 3 requests at the same time (protects rate limits) |

**Experiment:** time a loop of three `invoke` calls and compare it with `batch`. On cloud providers, `batch` is usually much faster. On a laptop running one local model, the gain is smaller, because the model can only do so much at once.

## Key Takeaways

1. Every chat model follows one rule: **messages in, one `AIMessage` out**.
2. Input can be a **string**, a list of **dictionaries**, or a list of **message objects**; all become messages.
3. Use **`.text`** for the answer. `.content` can be a list on some providers; **`.content_blocks`** gives a standard format for every provider.
4. `.usage_metadata` gives tokens; `.response_metadata` holds provider details whose **key names differ** between providers.
5. **`.profile`** tells you a model's capabilities, but can be missing: always use `llm.profile or {}`.
6. Use **`batch`** for many independent requests, with `max_concurrency` to stay within limits.

**Practice:** Write `compare_models.py` that asks the same question to two models from your `.env` options (for example, Ollama and Gemini) using `init_chat_model` directly, and prints a table with: provider, reply text, input tokens, output tokens, finish reason, and `max_input_tokens` from the profile (or "unknown").
