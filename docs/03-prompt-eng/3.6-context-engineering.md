## Module 3: Prompt Engineering

### 3.6 Context Engineering

---

## 1. From Prompt Engineering to Context Engineering

| | Prompt engineering | Context engineering |
|---|---|---|
| Focus | Writing and organizing the **instructions** | Choosing **everything** the model sees in one request |
| Question | "How do I phrase this?" | "What information does the model need, in what form, and what should stay out?" |
| Scope | The system prompt and user message | Instructions, examples, documents, history, user data, date, schema |

Anthropic describes context engineering as curating "the optimal set of tokens" for each request. LangChain calls providing the right information in the right format "the number one job of AI Engineers," because most LLM apps fail not because the model is weak, but because **the right context was not passed to it**.

> **Mental Model: Mise en Place**
> Before service, a good chef prepares exactly the ingredients each dish needs, measured and in order. Not the whole pantry. Context engineering is mise en place for the model: the right ingredients, the right amounts, in the right order, prepared before every request.

---

## 2. The Context Stack

Every request is assembled from layers. You decide what goes into each one.

| Layer | Example | Changes |
|---|---|---|
| 1. **Instructions** | Role, rules, output format (Lessons 3.1–3.2) | Rarely |
| 2. **Examples** | 3–5 canonical examples (Lesson 3.3) | Rarely |
| 3. **Reference knowledge** | Relevant policy sections, product data | Per request |
| 4. **User and runtime data** | Customer name, order status, today's date | Per request |
| 5. **Conversation history** | Recent turns, or a summary of older ones (Lesson 2.2) | Every turn |
| 6. **The current input** | The customer's latest message | Every turn |
| 7. **Output schema** | The structure to return (Lesson 3.5) | Rarely |

---

## 3. The Core Principle: Less, but Better

From Lesson 2.2: long contexts cost more, run slower, and can **reduce quality** ("context rot"). Anthropic describes the model as having an **attention budget**: every token added draws on it.

**Goal: the smallest set of high-signal tokens that makes a correct answer most likely.**

| Low-signal context (remove) | High-signal context (keep) |
|---|---|
| The whole 40-page policy handbook | The 2 policy sections that match the question |
| Every past message from a long chat | The last few turns plus a short summary |
| The full order record with 30 fields | Order number, item, delivery date, status |
| Repeated or contradictory instructions | One clear rule per behavior |

---

## 4. Four Context Operations

| Operation | What you do | Example |
|---|---|---|
| **Select** | Include only what is relevant to this request | Retrieve the refund section, not the whole handbook |
| **Compress** | Shrink what is useful but too long | Summarize old chat turns; keep only needed order fields |
| **Order** | Put things where they work best | Stable content first, documents before the question |
| **Exclude** | Keep out noise, secrets, and risky data | Remove card numbers; never put API keys in prompts |

> **Mental Model: Select, Compress, Order, Exclude**
> Before every request, ask four questions: **What's relevant? Can it be shorter? Where does it go? What must stay out?**

---

## 5. System Prompts at the Right Altitude

Anthropic recommends writing system prompts at the **right altitude**: specific enough to guide behavior, but not so rigid that they break on new cases.

| Too low (brittle) | Right altitude | Too high (vague) |
|---|---|---|
| "If the customer says 'refund' and the item is headphones and the date is more than 7 days ago, say exactly: ..." | "Apply the refund policy using the delivery date. If outside the refund window, offer warranty repair." | "Be helpful with refunds." |
| Breaks on any new wording | Handles new cases correctly | The model guesses |

---

## 6. Ordering for Quality and Cost

| Rule | Why |
|---|---|
| **Stable content first** (instructions, examples, fixed policy) | Enables **prompt caching**: providers reuse an identical prompt **prefix** at a lower price and latency |
| **Dynamic content last** (date, user data, current message) | A change early in the prompt breaks the cache for everything after it |
| **Long documents before the question** | Better answers on long inputs (Lesson 3.2) |

OpenAI's caching guide is explicit: put stable instructions and shared reference material first, and move timestamps and user-specific details to the end. Caching is automatic on OpenAI for prompts of at least 1,024 tokens (GPT-5.6 and later), and cached tokens are reported in `usage.prompt_tokens_details.cached_tokens`.

**Note:** in Lesson 2.4 you added today's date to the system prompt. That is correct for accuracy, but for caching, put the date in a **later** part of the context (for example, the user message), so the stable system prompt stays identical across requests.

## 8. OpenAI SDK Example

### Example 1: Everything vs Curated Context

Create `context_compare.py`:

```python
from datetime import date

from llm import get_client
from shop_data import ORDER, POLICY_SECTIONS

client, model = get_client()

SYSTEM = "You are a ShopPK support assistant. Answer only from the context. Keep replies under 60 words."
QUESTION = "My headphones from order #4821 stopped working. Can I get a refund?"
TODAY = date(2026, 10, 10)


def ask(context: str) -> tuple[str, int]:
    response = client.chat.completions.create(
        model=model,
        messages=[
            {"role": "system", "content": SYSTEM},
            {"role": "user", "content": f"{context}\n\nToday: {TODAY:%d %B %Y}\n<question>{QUESTION}</question>"},
        ],
        temperature=0,
    )
    return response.choices[0].message.content, response.usage.prompt_tokens


everything = "\n".join(f"<{name}>{text}</{name}>" for name, text in POLICY_SECTIONS.items())
everything += f"\n<order>{ORDER}</order>"

curated = (
    f"<refunds>{POLICY_SECTIONS['refunds']}</refunds>\n"
    f"<warranty>{POLICY_SECTIONS['warranty']}</warranty>\n"
    f"<order>Item: {ORDER['item']} (electronics), delivered {ORDER['delivered_on']}</order>"
)

for name, context in [("EVERYTHING", everything), ("CURATED", curated)]:
    answer, tokens = ask(context)
    print(f"--- {name} ({tokens} input tokens) ---\n{answer}\n")
```

**What to notice:** the curated context uses far fewer tokens and contains only what matters: the refund window, the warranty, and the delivery date. The correct answer: 9 days have passed, which is outside the 7-day electronics refund window, so the customer is offered a **warranty repair**. On a 40-page real handbook, the difference in cost and accuracy is much larger.

## 9. LangChain Examples

### Example 2: A Context Builder with a Token Budget

In production, context is assembled by **code**, from several sources, within a budget.

Create `lc_context_builder.py`:

```python
from datetime import date

from langchain.messages import HumanMessage, SystemMessage
from langchain_core.messages.utils import count_tokens_approximately
from langchain_ollama import ChatOllama

from shop_data import CUSTOMER, ORDER, POLICY_SECTIONS

SYSTEM = SystemMessage(
    "You are a ShopPK support assistant. Answer only from the context sections. "
    "If the answer is not in the context, say a human agent will follow up within 24 hours. "
    "Keep replies under 60 words."
)


def build_context(question: str, policy_keys: list[str], budget: int = 300) -> HumanMessage:
    sections = {
        "policy": "\n".join(POLICY_SECTIONS[key] for key in policy_keys),
        "customer": f"Name: {CUSTOMER['name']}. City: {CUSTOMER['city']}.",
        "order": f"{ORDER['order_number']}: {ORDER['item']} ({ORDER['category']}), "
                 f"delivered {ORDER['delivered_on']}, status {ORDER['status']}.",
        "today": date(2026, 10, 10).strftime("%d %B %Y"),
        "question": question,
    }
    text = "\n".join(f"<{name}>{content}</{name}>" for name, content in sections.items())

    print("Context report:")
    for name, content in sections.items():
        print(f"  {name:<9} ~{count_tokens_approximately([HumanMessage(content)]):>4} tokens")

    total = count_tokens_approximately([SYSTEM, HumanMessage(text)])
    print(f"  TOTAL     ~{total:>4} tokens (budget {budget})\n")
    if total > budget:
        raise ValueError("Context is over budget: select fewer sections or compress them.")
    return HumanMessage(text)


if __name__ == "__main__":
    llm = ChatOllama(model="gemma4:e2b", temperature=0)
    message = build_context(
        "My headphones from order #4821 stopped working. Can I get a refund?",
        policy_keys=["refunds", "warranty"],
    )
    print(llm.invoke([SYSTEM, message]).content)
```

| Code | Meaning |
|---|---|
| `sections` | Each source of context in its own named section |
| Only needed customer and order fields | **Compress**: 2 customer fields instead of 5; no internal notes, tracking, or card number |
| `count_tokens_approximately` | Measures each section, so you can see what is expensive |
| `budget` check | Fails loudly instead of silently sending a huge prompt |
| Order of sections | Policy and data first, the question last |

### Example 3: Select Policy Sections Automatically

Choosing `policy_keys` by hand doesn't scale. Use embeddings to select the most relevant sections for each question (this is the core idea behind RAG, coming in a later module).

Create `lc_context_select.py`:

```python
from langchain.messages import HumanMessage, SystemMessage
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_ollama import ChatOllama, OllamaEmbeddings

from shop_data import POLICY_SECTIONS

store = InMemoryVectorStore.from_texts(
    texts=list(POLICY_SECTIONS.values()),
    embedding=OllamaEmbeddings(model="embeddinggemma"),
    metadatas=[{"section": name} for name in POLICY_SECTIONS],
)

llm = ChatOllama(model="gemma4:e2b", temperature=0)
SYSTEM = SystemMessage("You are a ShopPK support assistant. Answer only from the policy. Under 50 words.")

questions = [
    "Can I pay with JazzCash, and is cash on delivery possible?",
    "How long will delivery to Multan take?",
    "How many points do I need for a discount?",
]

for question in questions:
    selected = store.similarity_search(question, k=2)
    policy = "\n".join(f"<{doc.metadata['section']}>{doc.page_content}</{doc.metadata['section']}>" for doc in selected)

    print(f"Q: {question}")
    print(f"   selected: {[doc.metadata['section'] for doc in selected]}")
    answer = llm.invoke([SYSTEM, HumanMessage(f"{policy}\n\n<question>{question}</question>")])
    print(f"A: {answer.content}\n")
```

**What to notice:** each question receives only the **2 most relevant** of 8 sections. You should see `payments` selected for JazzCash, `delivery` for Multan, and `loyalty` for points. Sections like careers and privacy don't reach the model when they are irrelevant. Check the `selected` line: if the wrong section is chosen, the answer will be wrong too, so selection quality matters as much as the prompt.

### Example 4: Compress History with a Running Summary

From Lesson 2.2: trimming forgets early facts. A better option for long chats: **summarize** old turns and keep the recent ones word for word.

Create `lc_context_summary.py`:

```python
from langchain.messages import AIMessage, HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

llm = ChatOllama(model="gemma4:e2b", temperature=0)

history = [
    HumanMessage("Hi, I'm Ali from Multan. I ordered wireless headphones, order #4821."),
    AIMessage("Hi Ali! Thanks for your order. How can I help?"),
    HumanMessage("They were delivered on 1 October."),
    AIMessage("Thanks for confirming the delivery date."),
    HumanMessage("Do you have the same headphones in black?"),
    AIMessage("Yes, the black version is in stock."),
]

KEEP_RECENT = 2  # keep the last turn (one user message + one reply) word for word
old, recent = history[:-KEEP_RECENT], history[-KEEP_RECENT:]

summary = llm.invoke([
    SystemMessage("Summarize the key facts from this support chat in at most 3 short bullet points: "
                  "customer name, order details, dates. No other text."),
    *old,
]).content

print("SUMMARY OF OLDER TURNS:\n", summary, "\n")

context = [
    SystemMessage("You are a ShopPK support assistant. Keep replies under 50 words."),
    SystemMessage(f"Summary of earlier conversation:\n{summary}"),
    *recent,
    HumanMessage("My headphones stopped working. What's my order number and what can you do?"),
]

print("REPLY:", llm.invoke(context).content)
```

| Part of the context | Content |
|---|---|
| Summary | Name, city, order #4821, delivered 1 October (compressed) |
| Recent turns | The black headphones question and answer (exact) |
| New message | The current question |

**What to notice:** the reply can still use the order number and delivery date from the start of the chat, but the old turns now take a few short lines instead of four full messages. In production, the summary is updated every few turns and saved with the conversation.

### Example 5: Exclude Sensitive and Noisy Data

Some data must **never** reach the model: card numbers, passwords, internal notes. Remove it in code before building the context.

Create `lc_context_exclude.py`:

```python
import re

from langchain.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

from shop_data import CUSTOMER, ORDER

ALLOWED_ORDER_FIELDS = ["order_number", "item", "category", "delivered_on", "status"]
ALLOWED_CUSTOMER_FIELDS = ["name", "city", "loyalty_points"]


def redact(text: str) -> str:
    text = re.sub(r"\b\d(?:[ -]?\d){12,15}\b", "[CARD REMOVED]", text)
    text = re.sub(r"\b03\d{2}-?\d{7}\b", "[PHONE REMOVED]", text)
    return text


safe_order = {key: ORDER[key] for key in ALLOWED_ORDER_FIELDS}
safe_customer = {key: CUSTOMER[key] for key in ALLOWED_CUSTOMER_FIELDS}

customer_message = "Hi, my card 4111 1111 1111 1111 was charged twice. Call me on 0300-1234567."
clean_message = redact(customer_message)

print("Order fields sent:   ", list(safe_order))
print("Customer fields sent:", list(safe_customer))
print("Message sent:        ", clean_message, "\n")

llm = ChatOllama(model="gemma4:e2b", temperature=0)
reply = llm.invoke([
    SystemMessage("You are a ShopPK support assistant. Keep replies under 50 words."),
    HumanMessage(
        f"<customer>{safe_customer}</customer>\n<order>{safe_order}</order>\n"
        f"<customer_message>{clean_message}</customer_message>"
    ),
])
print("REPLY:", reply.content)
```

| Technique | Purpose |
|---|---|
| **Allow-list** of fields | Only send fields the model needs; new sensitive fields are excluded by default |
| `redact()` with regular expressions | Removes card numbers (13–16 digits, with or without spaces or dashes) and Pakistani mobile numbers, even when the customer types them |
| Internal notes, warehouse IDs excluded | They add tokens and can leak into replies |

**What to notice:** the message becomes `"my card [CARD REMOVED] was charged twice. Call me on [PHONE REMOVED]."` The model can still help with the double charge, but never sees the private numbers. Real systems use dedicated PII-detection tools; this example shows the principle.

## 10. Context Engineering Checklist

| Check | Done |
|---|---|
| **Select:** only relevant policy sections, records, and examples are included | |
| **Compress:** long history is summarized; records are reduced to needed fields | |
| **Order:** stable content first, dynamic data and the question last | |
| **Exclude:** secrets, PII, and internal data are removed by an allow-list or redaction | |
| The system prompt is at the right altitude: clear principles, not brittle scripts | |
| Context size is measured and kept within a budget | |
| Missing information has a defined fallback | |

---

## Key Takeaways

1. **Context engineering** means choosing everything the model sees, not just writing instructions. It is the main lever for reliable LLM apps.
2. Aim for **the smallest set of high-signal tokens** that makes a correct answer likely.
3. Use the four operations: **Select, Compress, Order, Exclude**.
4. Write system prompts at the **right altitude**: guiding principles, not brittle scripts or vague wishes.
5. Put **stable content first and dynamic content last** for better caching, and documents before the question for better answers.
6. Build context **with code**, measure its size, and never send secrets or unneeded personal data.

**Practice:** Combine Examples 2, 3, and 5 into one `build_context(question)` function: select policy sections with embeddings, add allow-listed customer and order fields, redact the user message, check the token budget, and print a context report before calling the model.
