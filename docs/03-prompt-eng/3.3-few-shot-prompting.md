## Module 3: Prompt Engineering

### 3.3 Few-Shot Prompting and Examples

---

## 1. Show, Don't Just Tell

Some things are hard to describe in instructions but easy to **show**: a tone of voice, an exact output format, or where the line falls between two similar categories.

| Term | Meaning |
|---|---|
| **Zero-shot** | Instructions only, no examples |
| **One-shot** | Instructions plus one example |
| **Few-shot** | Instructions plus several examples (usually 3–5) |

Examples are one of the most reliable ways to control a model's **format, tone, and decisions**. Anthropic's prompting guide recommends **3–5 examples** for best results.

> **Mental Model: Training a New Cashier**
> You can hand a new cashier a rulebook, or you can let them watch you serve three customers. Most people learn faster from watching. Few-shot prompting lets the model "watch" a few correct answers before it serves your customer.

---

## 2. When to Use Examples

| Use examples when... | Example |
|---|---|
| The **output format** must be exact | Always reply as `category: billing` |
| The **tone or style** is hard to describe | "Friendly but brief, like our support team" |
| Categories have **blurry edges** | Is "charged but never shipped" billing or delivery? |
| The task is **unusual** or domain-specific | Labelling legal clauses, medical notes, Urdu slang |

| Zero-shot is often enough when... |
|---|
| The task is common and simple (summarize, translate) |
| You need to save tokens on every request |
| You are using structured output with a strict schema (Lesson 3.5) |

---

## 3. Writing Good Examples

| Quality | Meaning | Bad sign |
|---|---|---|
| **Relevant** | Look like real inputs your app receives | Toy examples unlike real data |
| **Diverse** | Cover different categories, lengths, and edge cases | All examples are short and positive |
| **Balanced** | Each label appears a fair number of times | 4 "billing" examples, 1 "technical" |
| **Consistent** | Every example follows your instructions exactly | An example breaks the word limit you set |
| **Clearly marked** | Wrapped in `<example>` tags or sent as message pairs | Examples blend into the instructions |

### Common Pitfalls

| Pitfall | What happens | Fix |
|---|---|---|
| Examples too similar | The model copies their wording or length | Vary phrasing, length, and topic |
| Label imbalance | The model over-predicts the common label | Balance the examples |
| Examples contradict instructions | The model follows the examples, not the rules | Check every example against every rule |
| Too many examples | Higher cost and latency for little gain | Start with 3–5; add only if tests improve |
| Real customer data in examples | Privacy risk | Use realistic but invented examples |

> **Mental Model: Examples Are Louder Than Instructions**
> When examples and instructions disagree, models usually follow the examples. Treat your examples as the **strongest part of the prompt**, and check them carefully.

### Examples for Reasoning Models

For reasoning models (Lesson 3.4), Anthropic's guide suggests showing each example as **problem, method, answer**. The model then applies the same method in its own thinking.

---

## 4. Two Ways to Add Examples

| Method | How it works | Best for |
|---|---|---|
| **Message pairs** | A fake conversation: user message, ideal assistant reply, repeated | Classification and short, exact outputs |
| **XML `<examples>` in the system prompt** | Examples written inside tags in the instructions | Longer examples, tone, and format |

**Message pairs:**

```text
SYSTEM:    Classify the support ticket. Reply with one label.
USER:      I was charged twice for one order.
ASSISTANT: billing
USER:      My parcel has not arrived after 10 days.
ASSISTANT: delivery
USER:      <the real ticket>
```

**XML examples:**

```xml
<examples>
  <example>
    <ticket>I was charged twice for one order.</ticket>
    <label>billing</label>
  </example>
  <example>
    <ticket>My parcel has not arrived after 10 days.</ticket>
    <label>delivery</label>
  </example>
</examples>
```

---

## 5. Static vs Dynamic Examples

| | Static examples | Dynamic examples |
|---|---|---|
| How | The same examples in every request | The most **similar** examples are chosen for each request |
| Pros | Simple, predictable, cache-friendly | More relevant; scales to hundreds of stored examples |
| Cons | May not match unusual inputs | Needs embeddings and a vector store |

Dynamic selection uses **embeddings** (text turned into numbers that capture meaning) to find stored examples closest to the new input. You will use embeddings properly in the RAG module; Example 5 is a first look.

**The task in all examples:** classify ShopPK support tickets into one of five labels:

| Label | Covers |
|---|---|
| `billing` | Payments, charges, refunds, invoices, **any money problem** |
| `delivery` | Shipping, tracking, late or missing parcels (no money issue) |
| `technical` | Website, app, login, or product not working |
| `account` | Profile, password, email, address changes |
| `other` | Everything else |

The tricky rule: **if money is involved, it is `billing`**, even when the ticket also mentions delivery. This is exactly the kind of rule examples teach well.

## 7. OpenAI SDK Example

### Example 1: Zero-Shot vs Few-Shot

Create `fewshot_compare.py`:

```python
from llm import get_client

client, model = get_client()

INSTRUCTIONS = (
    "Classify the ShopPK support ticket into one label: billing, delivery, technical, account, other. "
    "Reply with the label only, in lowercase."
)

EXAMPLES = [
    ("I was charged twice for order #5521.", "billing"),
    ("My parcel has not moved from Karachi for a week.", "delivery"),
    ("The app crashes when I open my cart.", "technical"),
    ("I want to change the phone number on my profile.", "account"),
    ("I paid for express delivery but the parcel came late. I want the extra fee back.", "billing"),
]

TICKETS = [
    "My order shows delivered but I never got it, and I already paid. Please return my money.",
    "Can you update my delivery address in my account settings?",
    "Do you sell gift cards?",
]


def classify(ticket: str, few_shot: bool) -> str:
    messages = [{"role": "system", "content": INSTRUCTIONS}]
    if few_shot:
        for example_ticket, label in EXAMPLES:
            messages.append({"role": "user", "content": example_ticket})
            messages.append({"role": "assistant", "content": label})
    messages.append({"role": "user", "content": ticket})

    response = client.chat.completions.create(model=model, messages=messages, temperature=0, max_tokens=5)
    return response.choices[0].message.content.strip().lower()


for ticket in TICKETS:
    print(f"{ticket}\n  zero-shot: {classify(ticket, False):<10} few-shot: {classify(ticket, True)}\n")
```

**Expected labels:** `billing` (money involved), `account` (a profile setting, not a parcel), `other`.

**What to notice:** zero-shot often labels the first ticket `delivery` because it mentions delivery. The few-shot version has seen the express-fee example, which shows that **money beats delivery**.

## 8. LangChain Examples

### Example 2: Few-Shot as Message Pairs

Create `lc_fewshot_messages.py`:

```python
from langchain.messages import AIMessage, HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

EXAMPLES = [
    ("I was charged twice for order #5521.", "billing"),
    ("My parcel has not moved from Karachi for a week.", "delivery"),
    ("The app crashes when I open my cart.", "technical"),
    ("I want to change the phone number on my profile.", "account"),
    ("I paid for express delivery but the parcel came late. I want the extra fee back.", "billing"),
]

SYSTEM = SystemMessage(
    "Classify the ShopPK support ticket into one label: billing, delivery, technical, account, other. "
    "If money is involved, the label is billing. Reply with the label only, in lowercase."
)


def build_messages(ticket: str) -> list:
    messages = [SYSTEM]
    for example_ticket, label in EXAMPLES:
        messages.append(HumanMessage(example_ticket))
        messages.append(AIMessage(label))
    messages.append(HumanMessage(ticket))
    return messages


if __name__ == "__main__":
    llm = ChatOllama(model="gemma4:e2b", temperature=0, num_predict=5)
    ticket = "My order shows delivered but I never got it, and I already paid. Please return my money."
    print(llm.invoke(build_messages(ticket)).content.strip().lower())
```

| Code | Meaning |
|---|---|
| `HumanMessage(example_ticket)` + `AIMessage(label)` | One example: a pretend user turn and the ideal assistant reply |
| `build_messages(ticket)` | System prompt, then all examples, then the real ticket last |
| `num_predict=5` | A label needs only a few tokens (Lesson 2.3) |

### Example 3: XML Examples for Tone and Format

Labels are easy. Examples really shine for **style**. Here they teach the exact reply format and tone.

Create `lc_fewshot_style.py`:

```python
from langchain.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

SYSTEM = SystemMessage("""# Identity
You are a ShopPK support assistant.

# Instructions
- Reply in the same style as the examples: a short greeting with the name, one or two sentences, one next step.
- Maximum 45 words. No emojis. No markdown.

# Examples
<examples>
  <example>
    <customer_email>Hi, I'm Sara. My order #3310 is late.</customer_email>
    <reply>Hi Sara, sorry for the wait. Your order #3310 is with our courier and should arrive within 2 working days. You can track it at shoppk.pk/track.</reply>
  </example>
  <example>
    <customer_email>This is Bilal. I can't log in to the app.</customer_email>
    <reply>Hi Bilal, sorry about the trouble. Please reset your password at shoppk.pk/reset and try again. If it still fails, reply here and we will help you directly.</reply>
  </example>
  <example>
    <customer_email>Ayesha here. I was charged twice.</customer_email>
    <reply>Hi Ayesha, sorry about the double charge. We have flagged it for our billing team. Please reply with your order number so we can refund the extra payment.</reply>
  </example>
</examples>""")

llm = ChatOllama(model="gemma4:e2b", temperature=0.3)

email = "<customer_email>Hello, I'm Usman. The shoes I got are one size too small.</customer_email>"
reply = llm.invoke([SYSTEM, HumanMessage(email)]).content

print(reply)
print(f"\n[{len(reply.split())} words]")
```

**What to notice:** the reply copies the **pattern** (greeting with name, short apology, one next step) without copying the exact words. Remove the `# Examples` section and compare.

### Example 4: Measure the Difference

"It looks better" is not enough. Test both prompts on a small **labelled test set** and measure accuracy.

Create `lc_fewshot_eval.py`:

```python
from langchain.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

from lc_fewshot_messages import SYSTEM, build_messages

TEST_SET = [
    ("My order shows delivered but I never got it, and I already paid. Please return my money.", "billing"),
    ("The parcel tracking page has not updated in four days.", "delivery"),
    ("The checkout button does nothing when I tap it.", "technical"),
    ("Please change the email address on my account.", "account"),
    ("Why was I charged a delivery fee on a free-shipping order?", "billing"),
    ("Do you have a physical shop in Multan?", "other"),
]

llm = ChatOllama(model="gemma4:e2b", temperature=0, num_predict=5)

zero_shot_inputs = [[SYSTEM, HumanMessage(ticket)] for ticket, _ in TEST_SET]
few_shot_inputs = [build_messages(ticket) for ticket, _ in TEST_SET]

zero_shot = [reply.content.strip().lower() for reply in llm.batch(zero_shot_inputs)]
few_shot = [reply.content.strip().lower() for reply in llm.batch(few_shot_inputs)]

zero_correct = few_correct = 0
for (ticket, expected), zero, few in zip(TEST_SET, zero_shot, few_shot):
    zero_correct += zero == expected
    few_correct += few == expected
    print(f"expected={expected:<10} zero={zero:<10} few={few:<10} {ticket[:45]}")

print(f"\nZero-shot accuracy: {zero_correct}/{len(TEST_SET)}")
print(f"Few-shot accuracy:  {few_correct}/{len(TEST_SET)}")
```

| Code | Meaning |
|---|---|
| `TEST_SET` | Inputs with the correct answer, written by you |
| `llm.batch(...)` | Runs all test tickets in parallel |
| `zero == expected` | `True` counts as 1, `False` as 0 |

Two test tickets ("charged a delivery fee", "delivered but never got it") are designed around the **money beats delivery** rule. This is a tiny version of prompt evaluation, covered fully in Lesson 3.7.

### Example 5: Dynamic Examples with Embeddings

With many stored examples, pick only the **3 most similar** for each ticket.

Create `lc_fewshot_dynamic.py`:

```python
from langchain.messages import AIMessage, HumanMessage, SystemMessage
from langchain_core.vectorstores import InMemoryVectorStore
from langchain_ollama import ChatOllama, OllamaEmbeddings

EXAMPLE_BANK = [
    ("I was charged twice for order #5521.", "billing"),
    ("My refund has not reached my bank after 10 days.", "billing"),
    ("I paid for express delivery but it came late. I want the extra fee back.", "billing"),
    ("My parcel has not moved from Karachi for a week.", "delivery"),
    ("The courier says my address is incomplete.", "delivery"),
    ("The app crashes when I open my cart.", "technical"),
    ("I get an error when I try to pay by card on the website.", "technical"),
    ("I want to change the phone number on my profile.", "account"),
    ("How do I delete my ShopPK account?", "account"),
    ("Do you offer gift wrapping?", "other"),
]

store = InMemoryVectorStore.from_texts(
    texts=[ticket for ticket, _ in EXAMPLE_BANK],
    embedding=OllamaEmbeddings(model="embeddinggemma"),
    metadatas=[{"label": label} for _, label in EXAMPLE_BANK],
)

SYSTEM = SystemMessage(
    "Classify the ShopPK support ticket into one label: billing, delivery, technical, account, other. "
    "If money is involved, the label is billing. Reply with the label only, in lowercase."
)

llm = ChatOllama(model="gemma4:e2b", temperature=0, num_predict=5)


def classify(ticket: str, k: int = 3) -> str:
    similar = store.similarity_search(ticket, k=k)
    messages = [SYSTEM]
    for document in similar:
        messages.append(HumanMessage(document.page_content))
        messages.append(AIMessage(document.metadata["label"]))
    messages.append(HumanMessage(ticket))

    print(f"Ticket: {ticket}")
    for document in similar:
        print(f"  example: [{document.metadata['label']}] {document.page_content}")
    return llm.invoke(messages).content.strip().lower()


print("Label:", classify("The payment page shows an error and my card was charged anyway."))
```

| Code | Meaning |
|---|---|
| `OllamaEmbeddings(model="embeddinggemma")` | Turns text into vectors that capture meaning |
| `InMemoryVectorStore.from_texts(...)` | Stores the example tickets with their labels as metadata |
| `similarity_search(ticket, k=3)` | Finds the 3 stored examples closest in meaning to the new ticket |
| Selected examples become message pairs | Same pattern as Example 2, but chosen per request |

**What to notice:** for a payment error, the selected examples are mostly payment-related (billing and technical), which helps the model decide. The correct label is `billing`, because money was charged.

## 9. Few-Shot Checklist

| Check | Done |
|---|---|
| 3–5 examples to start | |
| Examples look like real inputs (but contain no real customer data) | |
| Every label or case type is represented fairly | |
| At least one example covers the tricky edge case | |
| Every example follows every instruction (length, format, tone) | |
| Examples are clearly marked (message pairs or `<example>` tags) | |
| Tested against zero-shot on a labelled test set | |

---

## Key Takeaways

1. **Few-shot prompting** teaches by example and is one of the most reliable ways to control format, tone, and decisions.
2. Start with **3–5 relevant, diverse, balanced** examples, and include the tricky cases.
3. **Examples are louder than instructions**: if they disagree, the model usually follows the examples.
4. Add examples as **message pairs** (best for labels and short outputs) or in **`<examples>` tags** (best for style and longer outputs).
5. **Dynamic examples** use embeddings to choose the most similar examples for each input.
6. Always **measure** few-shot against zero-shot on a labelled test set.
