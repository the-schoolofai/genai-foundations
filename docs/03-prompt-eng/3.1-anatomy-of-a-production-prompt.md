# Generative AI Foundations

## Module 3: Prompt Engineering

### 3.1 Anatomy of a Production Prompt

---

## 1. Chat Prompt vs Production Prompt

| | Chat prompt | Production prompt |
|---|---|---|
| Written by | A person, once | A developer, used thousands of times |
| Example | "write a reply to this customer" | A structured brief with role, rules, context, and output format |
| Goal | A good answer today | **The same quality on every request** |
| Tested | No | Yes, on many inputs |

A production prompt is **part of your code**. If it is vague, your app is unreliable.

> **Mental Model: The Job Brief**
> Imagine giving a task to a smart new employee on their first day. They know a lot, but nothing about **your** company, customers, or rules. A production prompt is the written brief you would give them: who they are, what to do, what they need to know, what to avoid, and what to hand back.

---

## 2. The Six Building Blocks

| # | Block | Question it answers | Example (support assistant) |
|---|---|---|---|
| 1 | **Role** | Who is the model? | "You are a support assistant for ShopPK, an online store in Pakistan." |
| 2 | **Task** | What exactly must it do? | "Write a reply to the customer message below." |
| 3 | **Context** | What does it need to know? | Store policy, order details, today's date |
| 4 | **Constraints** | What are the rules and limits? | "Under 80 words. Never promise refunds outside the policy." |
| 5 | **Examples** | What does good look like? | One sample message and ideal reply (Lesson 3.3) |
| 6 | **Output format** | What shape is the answer? | "Greeting, answer, one next step. Plain text, no markdown." |

Not every prompt needs all six, but every production prompt should **consider** all six.

> **Mental Model: Who, What, Know, Rules, Show, Shape**
> Role = **who**. Task = **what**. Context = **know**. Constraints = **rules**. Examples = **show**. Output format = **shape**.

---

## 3. System Prompt vs User Prompt

| | System prompt | User prompt |
|---|---|---|
| Written by | The developer | The end user (or your code, filled with user data) |
| Changes | Rarely; same for every request | Every request |
| Contains | Role, constraints, output format, stable context | The customer's message, the document, the question |
| Analogy | The job description | Today's ticket |

**Rule of thumb:** stable rules go in the **system** prompt; data that changes goes in the **user** prompt. This also makes prompts easier to test, reuse, and cache (Lesson 2.4).

---

## 4. Weak vs Production Prompt

**Weak prompt**

```text
Reply to this customer: My headphones stopped working after 10 days, I want my money back.
```

**Production prompt**

```text
SYSTEM
You are a support assistant for ShopPK, an online store in Pakistan.
Your goal is to resolve the customer's issue politely and accurately.

Store policy:
- Refunds are accepted within 14 days of delivery.
- Electronics have a 7-day refund window, then a 1-year warranty repair.
- Customers start a claim at shoppk.pk/support with their order number.

Rules:
- Use only the policy above. If something is not covered, say a human agent will follow up.
- Never promise a refund the policy does not allow.
- Keep the reply under 80 words, in a warm and professional tone.

Output format:
A greeting with the customer's name if known, the answer, and one clear next step.
Plain text only.

USER
Customer message: My headphones stopped working after 10 days, I want my money back.
```

| What changed | Why it matters |
|---|---|
| Role and goal | The model knows whose voice to use and what success means |
| Policy as context | The answer is grounded, not guessed (Lesson 2.4) |
| Explicit rules | Prevents costly mistakes, like promising refunds |
| Output format | Every reply has the same shape, so your app can rely on it |
| Data in the user prompt | The same system prompt works for every customer |

The correct answer here: the 7-day electronics refund window has passed, but the headphones are covered by the warranty repair.

---

## 5. Six Principles of Clear Prompts

| Principle | Weak | Strong |
|---|---|---|
| **Be specific** | "Make it short." | "Under 80 words." |
| **Say what to do, not only what to avoid** | "Don't be rude." | "Use a warm, professional tone." |
| **Explain why** | "Never use markdown." | "Plain text only, because replies are sent as SMS." |
| **Separate instructions from data** | Rules and customer text mixed together | Rules in the system prompt, data clearly labelled |
| **Define success** | "Help the customer." | "Resolve the issue or give one clear next step." |
| **Plan for missing information** | (nothing) | "If not covered, say a human agent will follow up." |

> **Mental Model: The Colleague Test**
> Before shipping a prompt, ask: *"If I gave this to a smart colleague with no background, would they produce exactly what I want?"* If they would need to ask questions, the model needs those answers in the prompt.

## 7. OpenAI SDK Example

### Example 1: Weak vs Production Prompt

Create `prompt_compare.py`:

```python
from llm import get_client

client, model = get_client()

MESSAGE = "My headphones stopped working after 10 days, I want my money back."

SYSTEM_PROMPT = """You are a support assistant for ShopPK, an online store in Pakistan.
Your goal is to resolve the customer's issue politely and accurately.

Store policy:
- Refunds are accepted within 14 days of delivery.
- Electronics have a 7-day refund window, then a 1-year warranty repair.
- Customers start a claim at shoppk.pk/support with their order number.

Rules:
- Use only the policy above. If something is not covered, say a human agent will follow up.
- Never promise a refund the policy does not allow.
- Keep the reply under 80 words, in a warm and professional tone.

Output format:
A greeting, the answer, and one clear next step. Plain text only."""

weak = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": f"Reply to this customer: {MESSAGE}"}],
    temperature=0.3,
)

production = client.chat.completions.create(
    model=model,
    messages=[
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": f"Customer message: {MESSAGE}"},
    ],
    temperature=0.3,
)

print("WEAK PROMPT:\n", weak.choices[0].message.content, "\n")
print("PRODUCTION PROMPT:\n", production.choices[0].message.content)
```

**What to notice:** the weak prompt often promises a refund or invents a process. The production prompt applies the 7-day rule, offers the warranty repair, and gives the claim link.

## 8. LangChain Examples

LangChain accepts prompts in three forms. All three reach the model as messages.

### Example 2: Three Ways to Send a Prompt

Create `lc_prompt_forms.py`:

```python
from langchain.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

llm = ChatOllama(model="gemma4:e2b", temperature=0.3)

# 1. Text prompt: one standalone request
print(llm.invoke("In one sentence, what is a system prompt?").content, "\n")

# 2. Message objects: system and user roles
messages = [
    SystemMessage("You are a patient computer science teacher. Answer in one sentence."),
    HumanMessage("What is a system prompt?"),
]
print(llm.invoke(messages).content, "\n")

# 3. Dictionary format: same as the OpenAI SDK
messages = [
    {"role": "system", "content": "You are a patient computer science teacher. Answer in one sentence."},
    {"role": "user", "content": "What is a system prompt?"},
]
print(llm.invoke(messages).content)
```

| Form | Use when |
|---|---|
| Text string | Quick, single requests with no rules |
| `SystemMessage` / `HumanMessage` | Production code; clear and readable |
| Dictionaries | Sharing prompts with OpenAI SDK code |

### Example 3: Build the Prompt from the Six Blocks

Keeping each block separate makes prompts easy to read, change, and reuse.

Create `lc_prompt_blocks.py`:

```python
from langchain.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

ROLE = "You are a support assistant for ShopPK, an online store in Pakistan."
TASK = "Write a reply to the customer message you receive."
CONTEXT = """Store policy:
- Refunds are accepted within 14 days of delivery.
- Electronics have a 7-day refund window, then a 1-year warranty repair.
- Unused items in original packaging can be exchanged within 14 days.
- Customers start a claim at shoppk.pk/support with their order number."""
CONSTRAINTS = """Rules:
- Use only the store policy. If something is not covered, say a human agent will follow up within 24 hours.
- Never promise anything the policy does not allow.
- Keep the reply under 80 words, in a warm and professional tone."""
OUTPUT_FORMAT = "Output format: a greeting, the answer, and one clear next step. Plain text only."


def build_system_prompt() -> str:
    return "\n\n".join([ROLE, TASK, CONTEXT, CONSTRAINTS, OUTPUT_FORMAT])


if __name__ == "__main__":
    llm = ChatOllama(model="gemma4:e2b", temperature=0.3)

    messages = [
        SystemMessage(build_system_prompt()),
        HumanMessage("Customer message: I received the wrong colour shoes yesterday. Can I exchange them?"),
    ]

    print(build_system_prompt())
    print("\n--- Reply ---")
    print(llm.invoke(messages).content)
```

**What to notice:** to change the tone or a policy, you edit **one block**, not one long paragraph. The `if __name__ == "__main__":` guard (Lesson 1.2) lets other files import `build_system_prompt` without running this demo.

### Example 4: One System Prompt, Many Requests

The system prompt stays the same; only the user message changes. `batch` runs all requests in parallel.

Create `lc_prompt_batch.py`:

```python
from langchain.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

from lc_prompt_blocks import build_system_prompt

llm = ChatOllama(model="gemma4:e2b", temperature=0.3)
system = SystemMessage(build_system_prompt())

customer_messages = [
    "My headphones stopped working after 10 days, I want my money back.",
    "I received the wrong colour shoes yesterday. Can I exchange them?",
    "Do you deliver to Quetta, and how long does it take?",
]

requests = [[system, HumanMessage(f"Customer message: {text}")] for text in customer_messages]

for text, reply in zip(customer_messages, llm.batch(requests)):
    print(f"CUSTOMER: {text}")
    print(f"REPLY:    {reply.content}\n")
```

**What to notice:** message 3 (Quetta delivery) is not in the policy. A good prompt makes the model hand it to a human instead of inventing a delivery time.

### Example 5: A/B Test Two Prompts

Professionals compare prompt versions on the **same inputs** before choosing one. This is the start of prompt evaluation (Lesson 3.7).

Create `lc_prompt_ab.py`:

```python
from langchain.messages import HumanMessage, SystemMessage
from langchain_ollama import ChatOllama

from lc_prompt_blocks import build_system_prompt

llm = ChatOllama(model="gemma4:e2b", temperature=0)

PROMPTS = {
    "A (weak)": "You are a helpful customer support assistant.",
    "B (production)": build_system_prompt(),
}

test_message = "Do you deliver to Quetta, and how long does it take?"

for name, system_prompt in PROMPTS.items():
    reply = llm.invoke([SystemMessage(system_prompt), HumanMessage(f"Customer message: {test_message}")])
    words = len(reply.content.split())
    invented = any(word in reply.content.lower() for word in ["days", "hours", "week"])
    print(f"--- Prompt {name} | {words} words | mentions a time: {invented} ---")
    print(reply.content, "\n")
```

| Check | Meaning |
|---|---|
| `words` | Does the reply respect the 80-word limit? |
| `mentions a time` | A rough signal that the model may have **invented** a delivery time |

Prompt B is allowed to mention "24 hours" for human follow-up, so read each reply as well. Simple automatic checks like these catch problems quickly, but a person (or a better test, Lesson 3.7) should confirm them.

## 9. Production Prompt Checklist

| Check | Done |
|---|---|
| Role and goal are clear | |
| The task is one specific action | |
| All needed context is included (policy, data, today's date) | |
| Rules say what to do, with limits as numbers | |
| There is an instruction for missing information | |
| The output format is defined | |
| Stable rules are in the system prompt; changing data is in the user prompt | |
| Tested on several inputs, including a tricky one | |

---

## Key Takeaways

1. A **production prompt** is code: written once, run thousands of times, and expected to be reliable.
2. Use the **six building blocks**: role, task, context, constraints, examples, output format.
3. Put **stable rules in the system prompt** and **changing data in the user prompt**.
4. Be specific, say what to do, explain why, and always plan for **missing information**.
5. Keep prompt blocks separate in code, and **test prompt versions on the same inputs**.

**Practice:** Write a production system prompt for a university admissions assistant using all six blocks. Test it with three questions, including one your context does not cover, and check that the assistant hands it to a human.
